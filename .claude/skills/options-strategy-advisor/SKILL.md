# Options Strategy Advisor

_Adapted from [tradermonty/claude-trading-skills](https://github.com/tradermonty/claude-trading-skills) `options-strategy-advisor` skill (MIT). The original is a standalone Black-Scholes + FMP-API tool for generic retail stock options education. jarvis-trader has two separate options subsystems: a disabled/stub `engine/options/` + `/options/*` router (do not use — see below), and a working, actually-running delayed-chain analytics pipeline (`engine/analysis/options_implied.py`, `engine/analysis/options_opportunity_board.py`, served at `/options-signals/*`) for SPY/QQQ only. This version routes through the working pipeline instead of reimplementing Black-Scholes, and is explicit about the gap for AAPL/TSLA and any other ticker._

## Why the `/options/*` router is off-limits

A Codex review of this skill (PR #815) found, by reading the actual source, that every `/options/*` endpoint this skill originally pointed to is non-functional or misleading. This is a static source-code finding, not an observed runtime check — nobody in this PR ran these endpoints against a live engine and watched the response; per this repo's verification discipline (`AGENTS.md`), "verified" is reserved for that. Confirmed by reading the source directly:

- **`GET /options/chain/{symbol}` always 404s.** `engine/options/chain_fetcher.py:fetch_chain()` builds an `OptionsChain` with `calls: list = []` and `puts: list = []` that are never populated, and `options_router.py` raises 404 whenever both lists are empty — which is always.
- **`GET /options/iv-rank/{symbol}` is not option IV rank.** `chain_fetcher.get_iv_rank()` computes a rank from 21-day close-to-close *historical* volatility, not option-implied volatility, and silently returns `50.0` (presented as "neutral") whenever data is missing.
- **`GET /options/greeks` always returns all-zero Greeks.** `options_router.py` instantiates a fresh `OptionsPositionManager()` per request, whose `GreeksMonitor` starts empty and is never rehydrated from the persisted position store.
- **`GET /options/positions` reads a store nothing populates.** `OptionsPositionManager.add_position()` has zero production callers (`grep -rn "add_position(" engine/` outside tests and the class itself returns nothing) — real option fills route through `OrderRouter`/Schwab and never reach this SQLite table, so it can read empty while real positions exist.
- **`GET /options/analyst/{symbol}` never returns a real verdict.** `agents/options_analyst.py:OptionsAnalyst._skew_signal/_term_signal/_gamma_signal` are hardcoded to always abstain (`return (0.0, False)`) and `_get_iv_rank()` always returns `None` — it's either "disabled" or `no_iv_data`, never a signal.
- **`POST /options/strategy/recommend` returns a fully-specified order, not a classification — and some of its concrete numbers are internally wrong, not just approximate.** `OptionsOrder` is documented in `strategy_executor.py` as "a complete options order ready for review or execution" with concrete strikes/premium/max-risk. `build_iron_condor()` estimates the combined credit as `0.6 × wing_width` but then computes `max_risk = (wing_width − net_premium / 2) × 100` instead of `(wing_width − net_premium) × 100` — for a 5-point wing that's $350 reported instead of the correct $200, a genuine math bug, not just a "rough" estimate. `build_covered_call()` similarly reports only the option premium as `max_profit`, omitting the stock leg's own upside. Calling this endpoint is fine for illustrating leg *shape* (strikes/expiry/right), but never report its `max_risk`/`max_profit`/`estimated_premium` fields as usable numbers — recompute payoff independently (Steps 3-5 below) rather than repeating what the endpoint returns, and never feed its output into an execution call.

None of this is a reason to reimplement Black-Scholes or Greeks in this skill (`engine/options/premium_calculator.py` and `greeks_monitor.py` still have correct math, they're just not wired to real data) — it's a reason to use the pipeline that actually works instead.

## What actually works: `/options-signals/*`

`engine/scripts/options_signals_snapshot.py` is *designed* to run every 30 minutes on weekday RTH, fetching free CBOE delayed chains plus VIX/VIX3M daily CSVs and writing `engine/data/options_signals/latest.json` — but nothing in `main.py`'s own scheduler (`AsyncIOScheduler`, checked directly — no job registers this script) runs it. The only scheduling wiring found anywhere in the repo is a manually-registered Windows Task Scheduler entry (`scripts/loops/register-options-signals-loop.ps1`); `engine/data/options_signals/latest.json` is also not a tracked file, so a fresh checkout or the documented Linux/cloud environment has no snapshot until someone runs the script or wires up an equivalent cron. `engine/routers/options_signals_router.py` serves the file read-only via `_read_latest_snapshot()`, which raises `HTTPException(404, "no options signals snapshot generated yet")` when it's missing — so **check for a 404 before assuming these endpoints have data**; if you get one, say the snapshot generator isn't running in this environment rather than treating it as a data outage:

- `GET /options-signals/latest` — the raw snapshot: ATM-straddle expected move (abs and %), delta-implied probability ladder, VIX/VIX3M term-structure regime, per symbol/horizon (`engine/analysis/options_implied.py`).
- `GET /options-signals/opportunity-board` — ranked, defined-risk bounded-strategy candidates computed from that same chain (`engine/analysis/options_opportunity_board.py`), explicitly self-labeled `"not a trade signal"` and analysis-only (no broker, no order routing).

**Coverage is SPY/QQQ by default** — `options_signals_snapshot.py`'s `--symbols` CLI argument accepts any comma-separated CBOE underlying and defaults to `DEFAULT_SYMBOLS`, so an operator running the generator with a different symbol list would produce a snapshot covering that list instead; neither `/options-signals/latest` nor `/options-signals/opportunity-board` enforces SPY/QQQ in code. Describe SPY/QQQ as the generator's *default*, not a hard limit, and inspect the actual `symbols`/`boards` keys in whatever snapshot is currently on disk before assuming AAPL/TSLA/other tickers are absent from it.

## The live options watchlist is SPY/QQQ only — AAPL/TSLA were removed

`engine/config.py`'s `OPTIONS_WATCHLIST` **code default** is `["SPY", "QQQ"]` as of 2026-08-17 — AAPL and TSLA were explicitly removed after failing daily-SMA-trend gate-v2 WFO certification (AAPL: sample-starvation, 1-3 OOS trades; TSLA: p_edge 0.50-0.56). `engine/CLAUDE.md`'s "Equities" table describing four live names (SPY/QQQ/AAPL/TSLA) is stale against this code default — don't cite it as current state. But the code default isn't necessarily the running engine's state: `POST /watchlist` (`engine/routers/watchlist_router.py`) appends any symbol to the live `settings.OPTIONS_WATCHLIST` at runtime, and `DELETE /watchlist/{symbol}` removes one — so query `GET /watchlist` for actual current membership before telling a user a symbol was removed from trading; only the *default* config file matches this doc, not necessarily the live process. Conveniently, the two default names are exactly the two with working analytics (`/options-signals/*` above) — but that's a *default*, not an enforcement: as noted in the "What actually works" section, the generator's `--symbols` argument accepts any CBOE underlying, so an operator-run snapshot could cover AAPL/TSLA too. Check the actual snapshot's `symbols`/`boards` keys before assuming AAPL/TSLA are absent from it. Absent that, there is no live options chain or Greeks source for AAPL, TSLA, or any other ticker. IV is a partial exception — see the Polygon `term_structure` fallback via `/options/skew/{symbol}` below. Pull current price from `GET /prices/snapshot?symbols=<TICKER>` if useful (check `is_live`, not just the watchlist — see the price-provenance note below), and otherwise treat AAPL/TSLA/etc. like the theoretical/educational path below, saying explicitly that no live options chain/Greeks analytics back the numbers.

Also: a watchlist symbol's paper fills are not automatically options trades — the scanner routes an options spread only when `trade_dec.is_spread` is set; otherwise it's an underlying-equity trade. Don't assume every SPY/QQQ paper fill in `/brokers/positions` is an option position — check what it actually is before describing it as one. In fact `/brokers/positions`' own `_normalise_paper_position()` doesn't carry option-specific fields at all (no strikes, expiry, or contract type — just symbol/direction/quantity/entry_price/entry_time), so it cannot answer "what does jarvis's options book actually look like" on its own; treat any options-specific detail from it as unavailable rather than inferring it.

## This skill never executes

**The real order path is broken, not merely un-gated — a correction to an earlier version of this section.** `main.py` sees `trade_dec.is_spread`, calls `execution/oms_v2.py:OMSManager.execute_options_spread()`, which builds an order dict with `is_options=True`, `is_spread=True`, `short_option_symbol`/`long_option_symbol` — but **no `asset_type` key**. `OrderRouter.route_order()` decides options-vs-equity routing with `is_options(order)`, which checks *only* `order.get("asset_type")` — so this order fails that check and falls through to the `else` branch, calling `schwab.place_paper_order(order)` (the equity path). Inside `place_paper_order()`, a *different* flag (`order.get("is_options")`, which the OMS dict does set to `True`) causes it to skip the equity safety check and instead call `submit_options_order()` — the *single-leg* options submitter — with a dict that has no `action` or `option_symbol` (those are spread-only fields). `submit_options_order()` rejects any `action` not in its allowed set immediately, before its own safety check ever runs, and returns `{"status": "error", "reason": "Invalid action..."}`. **Net effect: `SchwabConnector.submit_options_spread_order()` — the method with concrete strikes/premium that this section previously flagged as bypassing `risk/safety_layer.py` — is dead code with zero production callers** (confirmed: its only caller is `route_order()`'s options branch, which this order never reaches; its only other reference in the repo is a unit test). An options-spread order submitted through `execute_options_spread()` currently errors out on a schema mismatch rather than being placed unsafely. This is still a real engine bug (spreads can't be executed via this path at all as currently wired) — out of scope for this skill-only PR to fix — but it is not a live safety-layer bypass. Note `REQUIRE_HUMAN_APPROVAL = False` is the standing config (`.claude/rules/safety.md`), so `approval/service.py` is not a mandatory per-trade gate on any of these paths regardless.

This skill's job stops at analysis and education — say what a trade would look like, never place it, and never suggest bypassing the safety layer. This holds even when calling `/options/strategy/recommend`, whose response is a literal order object: report its fields as illustrative, never as a ticket to submit.

Before treating `/options-signals/latest` as current: check the top-level `generated_at`/`data_quality` (only ever "ok" or "partial" — a fetch either worked or didn't, this does NOT mean the quote is fresh), AND the specific horizon's own `quality`/`notes` (each horizon is independently marked `"degraded"` with a note when its `quote_ts` is >60 min old — a market holiday or feed outage can leave the top-level fields looking fine while the horizon you're using is stale). Don't stop at the top-level fields. `quote_ts` itself lives at the **symbol-block level** (`symbols[symbol].quote_ts`), not inside each horizon — `build_horizon()`'s own dict has no `quote_ts` field, so look for it one level up. Treat a **null `quote_ts`** there as unusable — `parse_chain()` can return `quote_ts=None` when CBOE's timestamp field is missing/unparseable, and the staleness check only degrades a horizon when `quote_ts is not None`, so a chain with no timestamp at all stays `quality="ok"` by omission, not because it's actually fresh. **The stored `quality` field is stale-checked only once, at generation time** — `build_symbol_block()` compares `quote_ts` against the 60-minute window using the timestamp *when the snapshot was written*, and `_read_latest_snapshot()` (`options_signals_router.py`) then returns that JSON verbatim on every later read with no re-check. If the generator stopped running (see the scheduler-wiring gap above) and the file just sits there, a horizon that was genuinely fresh at generation stays `quality="ok"` forever. Independently recompute staleness at read time using **two different thresholds, not one** — `options_implied.py` defines them separately: `now − generated_at` against the top-level `stale_after_s` (`STALE_AFTER_S = 2700`, 45 minutes) for the snapshot as a whole, and `now − symbols[symbol].quote_ts` against the 60-minute `QUOTE_STALE_S` for the specific symbol's quote — a snapshot 46-60 minutes old fails the first check even though the per-quote check alone wouldn't yet flag it.

Also check the **VIX/VIX3M regime block separately** — its own caching (in the snapshot generator) reuses the last successful fetch indefinitely on a refresh failure, annotating `regime.source` with "refresh failed" but not touching `regime.as_of_date` or the top-level `data_quality`. A weeks-old regime can silently sit behind an "ok" snapshot. Check `regime.source` for a "refresh failed" marker — but do NOT compare `regime.as_of_date` to literal today: the regime is built from "CBOE daily index CSVs (prior close; refreshed once per day)" by design, so a legitimately fresh regime is normally 1 trading day behind (more over a weekend/holiday). Compare against the most recent completed trading session instead of today, and rely on the "refresh failed" marker to catch genuine staleness.

Before treating `/prices/snapshot` output as a current price: check that symbol's `is_live` field, not just `as_of` — `as_of` is stamped at **fetch time** for every source, including `csv_cache`, so a prior-day close can carry a timestamp that looks fresh (confirmed by `engine/tests/test_actionable.py:test_board_cached_source_withheld_even_with_fresh_timestamp`, which exists specifically to catch this trap). When `is_live` is `false` (or `source` is `"unavailable"`), treat the price as unknown/stale regardless of how recent `as_of` looks — say "last available price via `<source>`, live status unconfirmed" rather than implying it's a current observation. **Even `is_live: true` isn't a hard guarantee of a current observation for the `polygon_stream` source specifically**: `prices_router.py` stamps `as_of = time.time()` at fetch time for every source, and `derive_is_live()` checks that stamp's own freshness — but `MarketDataManager.get_current_price()`'s Tier 3 fallback calls `PolygonStreamer.get_latest_bar()`, which returns whatever bar is cached with no check on the bar's own age, and that cache is retained across a stream disconnect. So a stale bar from before a disconnect can still be labeled `is_live: true` because the *fetch* was recent even though the *observation* wasn't. Treat `is_live: true` on `source: "polygon_stream"` as a slightly weaker signal than on `ibkr`/`schwab`, and prefer those sources when available for anything price-sensitive.

Before treating `/brokers/positions` as the current book: check `ibkr.connected`, `ibkr.positions_stale`, `schwab.connected`, and `reconciliation.health`. When both brokers are unreachable, `reconciliation.health` reports `"blind"` and the position arrays come back empty — that is "we don't know," not "flat." Never treat a blind or stale response as confirmation there's no existing exposure before suggesting adding risk. **`health` has a third state, `"partial"`, for exactly one broker connected** — `_build_reconciliation()` returns this when only one side is queryable, and it is not itself proof of a flat book either: if the disconnected broker is the one actually holding the options book (e.g. Schwab down, IBKR up), a `"partial"` response can still hide the entire options position while looking less alarming than `"blind"`. Treat `"partial"` the same as `"blind"` for the purpose of confirming no existing exposure — require all brokers relevant to the strategy being discussed to be connected and queryable before suggesting incremental risk. Note these checks aren't airtight either: `reconciliation.health` is computed from the pre-query `connected` booleans, not from whether the actual position query succeeded — if a broker reports connected but its `get_positions()` call raises internally, `get_broker_positions()` silently returns an empty array for that broker while `health` can still read `"ok"`. A clean-looking response is evidence, not proof, that no positions were missed.

Workflow for a SPY/QQQ question ("analyze my SPY iron condor", "what's SPY's expected move"):
1. Pull `/options-signals/latest` for the expected move / probability ladder / per-horizon `atm_iv` — never invent a stock price or IV, and never substitute the VIX/VIX3M term-structure numbers for a symbol's own `atm_iv` when pricing QQQ legs (VIX is an SPX-derived index; using it as QQQ's volatility input mis-prices the legs). VIX/VIX3M term structure is a separate regime signal, not a pricing input. The probability ladder itself is **delta-implied, not a real-world forecast**: `options_implied.py`'s own module docstring says it interpolates vendor *call* deltas (≈N(d1)), which slightly overstates the true risk-neutral P(close above) = N(d2), and explicitly disclaims any "validated predictive edge." Keep the "delta-implied (risk-neutral) approximation" framing when presenting these numbers — never call them "real" probabilities or an actual forecast. If the ladder also carries `p_touch`/`p_fail` (barrier-touch probability), those rest on a **second, separate approximation**: `prob_ladder()`'s own docstring says `p_touch = min(1, 2 × p_close_beyond)` is a zero-drift GBM reflection rule that ignores risk-neutral drift and the volatility smile, and is explicitly "not a calibrated first-passage probability." Keep the engine's own "reflection-implied" label on these — don't fold them into the same delta-implied caveat as if they were just another close probability; they carry an additional layer of approximation on top of it.
2. If the user wants a recommendation rather than an analysis of a specific trade they named, pull `/options-signals/opportunity-board` and check the returned board's own `status`, `candidate_count`, and each candidate's `reject_reasons` before presenting anything: when all candidates fail quality filters, `status` is `"degraded"`, `candidate_count` is `0`, but the `candidates` array still contains the rejected structures (the code falls back to showing rejects rather than an empty list). **`status` is a board-level field only** — `build_opportunity_board()`'s per-candidate serializer has no `status` key on individual candidates, so check the containing board's `status == "ok"` and that the specific candidate's own `reject_reasons` is empty; don't look for `status` on the candidate itself. Otherwise say the board found nothing that passed its own filters. It's explicitly labeled "not a trade signal," so frame any accepted candidate as a ranked payoff shape worth reviewing, not a recommendation to act on. A candidate's own `pop` field carries the **same delta-implied approximation as the probability ladder above, but the bias direction depends on structure** — `_p_above_interpolator()` derives the underlying call-delta probability from vendor deltas (≈N(d1), which exceeds the true N(d2)); for bull-call-debit and bull-put-credit structures `pop = p_above(breakeven)` directly, so it *overstates* the true probability the same way the ladder does, but for bear-call-credit and bear-put-debit structures `pop = 1 - p_above(breakeven)`, so taking the complement makes it *understate* the true probability instead. Don't present board `pop` as an ordinary, uncaveated probability of profit, and don't assume the bias always points the same direction — check which side of the trade the candidate is on. Two more limits on the board itself: (a) it always projects the symbol's **nearest** horizon — if the user asked for a specific DTE or "end of week," check the candidate's actual `expiry` and say the requested horizon isn't what's shown rather than silently substituting nearest-expiry; (b) its ranking `ev` is computed as a **binary payoff approximation** (`pop * max_gain - (1-pop) * max_loss`), which doesn't capture the continuous P/L between strikes on a vertical spread — don't cite `ev`/`ev_to_max_loss` as a precise expected value, just as the board's own (rough) ranking heuristic.
3. If they gave you specific legs, you can only sanity-check strikes/premium that actually appear in a returned board candidate (its own generated verticals) or the ATM straddle in `/options-signals/latest` — the snapshot has no arbitrary-strike chain lookup. For a leg the response doesn't cover (e.g. a wing of a 4-leg iron condor, or a strike far from ATM), say plainly that no matching quote is available rather than inventing one, then walk Steps 5-9 with whatever real numbers you do have.
4. For incremental-risk questions ("should I add another iron condor"), check `/brokers/positions` for the actual current book (with the connected/stale/health checks above) — not `/options/positions`, which reads an unpopulated store. Every source this endpoint aggregates has an option-detail gap: Schwab rows hit a real schema-mismatch bug (`_normalise_schwab_position()` looks for a nested `instrument` object and camelCase `averagePrice`/`marketValue`, but `SchwabConnector.get_positions()` returns flat snake_case fields, so every Schwab row silently defaults to `sec_type="EQUITY"` with null prices, even for real option positions) — **but the raw OCC option symbol string itself survives**: `_normalise_schwab_position()` still copies `instrument.symbol` (or the flat `symbol` field) through unmodified, and the connector already uses `OptionSymbol.parse_symbol()` elsewhere on identically-formatted strings, so strike/expiry/right can be recovered by parsing that preserved symbol before declaring option detail unavailable for a Schwab row specifically. IBKR rows (`_normalise_ibkr_position()`) carry only symbol/quantity/avg_price/market_price/sec_type with no strike, right, or expiry, and paper-tracker rows carry no option fields at all (see above) — for those two sources, option-leg detail is genuinely unavailable from this endpoint; don't trust their `sec_type` fields either.

## AAPL, TSLA, and any other ticker (theoretical / educational path)

No chain or Greeks source exists for AAPL, TSLA, or any ticker outside SPY/QQQ. There is one exception for IV specifically: `GET /options/skew/{symbol}` calls `chain_fetcher.get_term_structure()`, which fetches real Polygon option snapshots when `POLYGON_API_KEY` is configured — check the response's `term_available` flag before using `term_structure`. But its three values (`front_week_atm_iv`/`front_month_atm_iv`/`second_month_atm_iv`) come with **no expiry dates attached** — `front_n_expiries()` just grabs whichever three expirations are listed first, which for a weekly-options name may all be near-term weeklies rather than actually spanning a week/month/two-months. There's no way to match one of these three values to a specific 30-DTE or 60-DTE request, including via the "nearest label" — on a weekly-options name, `front_month_atm_iv` can just as easily be another near-term weekly rather than an actual ~30-day expiry, so the label itself isn't trustworthy as a maturity proxy. Don't use any of the three labels as a stand-in for a specific requested maturity; use a user-supplied IV or an HV estimate instead, and say that Polygon-derived IV for that specific maturity isn't available from this endpoint. **The ATM strike used to select these IVs is also picked from a stale spot**: `get_term_structure()` calls `spot_price_from_polygon()`, which fetches Polygon's `/v2/aggs/ticker/{symbol}/prev` — yesterday's close — not a current quote, so on a day the underlying has moved materially, the "ATM" strike this IV was read from may no longer be near the money even though the response's own `computed_at` looks current. Label `term_structure` a prior-close-selected approximation rather than implying it tracks today's actual ATM. **There's also no freshness check on the IV quote itself**: `fetch_chain_snapshot()` accepts whatever `implied_volatility` Polygon returns per contract with no per-contract quote/trade timestamp validation, and `get_term_structure()`'s own `computed_at` reflects when *this endpoint ran*, not when Polygon's IV was actually observed — an illiquid contract or an off-hours call can carry a stale IV that looks fresh by `computed_at` alone. Treat this IV's freshness as unknown and avoid using it for precise, account-specific sizing; it's fine for the rough educational/theoretical framing this section covers. **This endpoint can also stall the engine**: `GET /options/skew/{symbol}` is an `async` route, but its handler calls `get_pc_skew()`/`get_term_structure()` directly, and those call `_polygon_skew.py`'s `_polygon_get()`, which uses blocking `httpx.get(..., timeout=10.0)` with no executor offload — the term-structure path issues several of these serially. Under this engine's documented single-worker run command, a slow Polygon response blocks the event loop and delays every other in-flight request for up to that many × 10 seconds. Don't call this endpoint casually or repeatedly during a live session; treat a slow response as a shared-resource cost, not just latency for this one request. When `term_available` is `false` (no Polygon key, or the fetch failed), fall back to HV as usual. Pull current price from `/prices/snapshot?symbols=<TICKER>` if useful (checking its provenance fields per above); the theoretical Black-Scholes walkthrough below is fine for pricing, with user-supplied, Polygon-derived, or HV-estimated IV. Say explicitly which of those backs the IV you used — never imply full live options analytics exist for these names.

**Black-Scholes recap (education only — do not add this as new engine code):**

```
d1 = [ln(S/K) + (r + sigma^2/2) * T] / (sigma * sqrt(T))
d2 = d1 - sigma * sqrt(T)
Call = S*N(d1) - K*e^(-rT)*N(d2)
Put  = K*e^(-rT)*N(-d2) - S*N(-d1)
```

This is the zero-dividend **European** formula, but every underlying here (SPY, QQQ, AAPL, TSLA) trades **American-style** equity/ETF options. Two separate caveats, not one: (1) SPY, QQQ, and AAPL pay dividends — the formula as written overvalues calls and undervalues puts, and misses dividend-driven early-assignment risk around ex-dividend dates entirely; say so explicitly whenever dividends are relevant (longer-dated contracts, a trade spanning an ex-div date, or covered-call/protective-put analysis on a dividend payer) — `engine/options/premium_calculator.py`'s `black_scholes_price()` doesn't take a dividend yield either, so label the output "zero-dividend approximation" in that case. (2) **Independent of dividends**, a deep-ITM American put (including on a non-dividend payer like TSLA) can still be worth early-exercising to realize the strike proceeds sooner — European pricing can understate a deep-ITM put's value and its short holder's assignment risk regardless of dividend status. Label this pricer "European" for every American-style contract, not only the dividend-relevant cases, and flag early-exercise risk explicitly for any deep-ITM put analysis.

If you need to actually run these numbers rather than just quote them (e.g. to sanity-check a user-supplied example), reuse `engine/options/premium_calculator.py`'s Black-Scholes function (`black_scholes_price()`) in a throwaway Python `-c` snippet rather than writing a new pricer. **`pnl_at_expiry()` is narrower than it sounds**: it takes exactly one short and one long leg of the same right and computes a single vertical-spread payoff — it cannot represent a covered call's stock leg, a straddle/strangle's mixed-right legs, unequal leg quantities (ratio spreads), or a full iron condor/butterfly's four legs. Use it only for an actual vertical-spread component of a larger structure, and model every other leg (stock or option) and aggregate them yourself — don't feed a non-vertical structure into it and treat the result as the whole trade's P/L. **Also except `get_credit_spread_metrics()`'s `pop` field, which is inverted**: it returns `net_premium / spread_width` directly, so a $1 credit on a $5-wide spread reports 20% POP when the binary fair-value heuristic actually implies roughly the complement (~80%). Don't reuse that field; if a rough credit-spread POP is needed, compute `1 - (net_premium / spread_width)` by hand or use the delta-implied POP path instead (Step 5).

## Analysis workflow

### Step 1 — Gather inputs
Required: ticker, strategy, strikes, expiration(s), contract count, a **current, provenance-checked underlying price** (SPY/QQQ from `/prices/snapshot` or the snapshot's own spot; AAPL/TSLA/other from `/prices/snapshot?symbols=<TICKER>` checking `is_live`, or explicitly user-supplied) — every Black-Scholes price, Greek, and moneyness judgment depends on `S`, so if no live/provenance-checked price is available and the user hasn't supplied one, stop at an educational/structural explanation rather than run numbers off an invented or silently stale spot, and — for any multi-leg strategy (calendar, diagonal, ratio spread, any spread beyond a simple single vertical) — the **option right (call/put) and long/short action for every leg**. The strategy name plus strikes alone doesn't determine these: the same strikes can be built as a debit or credit, and reversing a leg's direction changes payoff and Greeks materially. Don't assume a "standard" construction — ask. Optional: IV (else HV, or for SPY/QQQ the matching horizon's `atm_iv` from `/options-signals/latest`), risk-free rate — default ~3-month T-bill is a short-tenor approximation only; for a leg expiring in a year or more (e.g. the LEAPS leg of a poor man's covered call) or a calendar/diagonal's two different expiries, use a maturity-matched Treasury/zero rate per leg where the yield curve isn't flat, or explicitly label the 3-month default as an approximation for that leg. **Stock-backed strategies** (covered call, protective put, collar) additionally need the underlying **share quantity and cost basis** — contract count alone doesn't establish that a short call is actually covered, and correct net delta, max profit, and breakeven all depend on the stock leg. Ask for it rather than assuming 100 shares/contract at an unstated basis. **Any multi-leg position** (not just ratio spreads — iron condors/butterflies, calendars, an existing position after a partial fill or partial close) needs a **quantity for every individual leg**, not one overall contract count, unless the user explicitly confirms a strategy's conventional 1:1 ratio applies. Unequal leg quantities silently change max loss, breakevens, and whether a short leg is actually covered — **ratio spreads** are simply the case where this is most obviously visible (1x2 vs. 2x3 on the same strikes have different Greeks, payoffs, and determine whether the structure is net-short, which Step 8's bounded-vs-unbounded distinction depends on), not the only case it matters for. **Cash-secured put**: nothing in the engine establishes that enough unencumbered cash actually exists to secure assignment (`strike × 100 × contracts`, net of the premium received). `GET /portfolio`'s `cash`/`cash_balance` fields are **not** a usable check here — `get_portfolio()` sets both equal to `current_equity` and hardcodes `margin_used` to 0.0, so neither reflects cash actually free of other positions/margin commitments. Ask the user directly for their broker's **settled/available cash specifically — not "buying power."** In a margin account, buying power includes borrowed capacity and can exceed `strike × 100 × contracts` even when unencumbered cash doesn't; accepting buying power as proof of "cash-secured" can certify a margin-backed short put as cash-secured when it isn't. If settled cash isn't confirmed, analyze it as a short put with unsecured/undefined margin exposure and say so, rather than assuming the "secured" label holds. **For an existing position** (not a hypothetical), also get the actual **entry/fill premium** — a theoretical current mark from Black-Scholes or the chain snapshot is not the trade's cost basis, and Step 5's max profit/loss/breakeven need the real number. If only a current theoretical mark is available, label the resulting P/L as hypothetical, not as the actual position's payoff.

### Step 2 — Volatility
SPY/QQQ: use the matching symbol/horizon's own `atm_iv` from `/options-signals/latest` as the pricing input — this is real option-derived IV, unlike `/options/iv-rank` (an HV proxy, do not use). Treat the snapshot's VIX/VIX3M term-structure classification (contango/backwardation/flat) as a separate regime signal for framing the trade, never as the volatility input for a specific symbol's Black-Scholes price (VIX is SPX-derived and will misprice QQQ). Note `atm_iv` is a single flat value for the whole horizon — the snapshot has no strike-specific IV, so pricing an OTM wing (iron condor, credit spread) with `atm_iv` ignores volatility skew. Label such a calculation a flat-volatility approximation, not the wing's actual IV. **`atm_iv` also only ever covers two horizons** — `select_expiries()`/`build_symbol_block()` expose just `nearest` (first expiry ≥ today) and `end_of_week`; there is no 30-DTE, 60-DTE, or LEAPS horizon. For a user-specified expiry that isn't one of those two, don't use either horizon's `atm_iv` as if it matched — check the horizon's own `expiry` field against the leg's actual expiry first, and if there's no match, say maturity-specific IV isn't available from this snapshot (fall back to HV or a user-supplied estimate instead). **`atm_iv` can also be silently one-sided**: `straddle_expected_move()` builds it as `sum(ivs) / len(ivs)` over whichever of the call/put legs actually had an IV — if CBOE only reported IV for one side, `atm_iv` is that single leg's IV, not a real call/put average, and nothing in `quality`/`notes` flags this case. There's no way to tell from the response alone whether it's one-sided; treat it as a best-available approximation rather than a guaranteed two-sided average. AAPL/TSLA/other tickers: `/options/skew/{symbol}`'s `term_structure` is usable **only when the user's requested expiry can't be pinned down at all** (i.e. as a rough regime signal, not as a specific maturity's IV) — per the earlier caveat, none of its three labels can be trusted to match a specific requested DTE, so for an actual pricing/sizing request with a real expiration, skip `term_structure` and use a user-supplied IV or an HV estimate from historical closes instead, saying which one backs the number. **The same one-sided-IV risk applies here too, separately**: `_polygon_skew.py`'s `atm_iv()` averages whichever of call/put IVs are actually present at the nearest strike (`sum(ivs)/len(ivs)`), and `get_term_structure()` still sets `term_available=true` as long as each of the first two expiries returns *some* value — a missing side isn't surfaced. Carry the same one-sided-approximation caveat for Polygon IV as for the CBOE snapshot above, not just "real Polygon-derived IV."

### Step 3 — Price the legs
SPY/QQQ: sanity-check against the delayed-chain-derived numbers actually present in `/options-signals/latest` (the ATM straddle) or a `/options-signals/opportunity-board` candidate — see the leg-coverage limit in Step 3 of the live-data workflow above. AAPL/TSLA/other tickers: quote the Black-Scholes formula inline (see above), don't hand-roll a new script for it.

### Step 4 — Greeks
There is no working live Greeks source for any symbol (`/options/greeks` always reports zero — see above). For a hypothetical trade, reuse `engine/options/greeks_monitor.py`'s `calculate_greeks()` in the same throwaway Python `-c` snippet as the Black-Scholes pricer (Step 3) rather than computing the five formulas by hand — it already has the tested formulas and the repo's own per-day theta / per-1%-move vega/rho conventions, and hand-deriving them risks silent formula or unit drift before the 100× aggregation. **`calculate_greeks()` uses the same zero-dividend European `d1`/`d2` model as `black_scholes_price()`** — so the same Black-Scholes recap caveats (dividend mispricing, American early-exercise risk on deep-ITM puts) apply to every Greek it returns, not just to the price. Don't present delta/theta/vega as more authoritative than the price they're derived from; carry the "zero-dividend, European" labeling into the Greeks output too when those caveats are relevant. Then scale each leg to dollar exposure as `per_share_greek × (+1 long / −1 short) × contract_quantity × 100` before summing across legs — equity options are 100-share contracts, so a raw per-share Greek understates exposure 100x if reported directly (e.g. one long call with delta 0.50 is ~$50 of underlying-equivalent exposure per $1 move, not $0.50). **The 100 multiplier itself isn't universal**: an option adjusted for a stock split, merger, or special dividend can have a non-standard OCC deliverable (more or fewer than 100 shares, or a cash component). For a user-supplied contract that could be adjusted (older LEAPS, a name with a recent corporate action), ask for or confirm the actual contract multiplier before applying 100 — don't assume standard deliverable silently. **Stock-backed strategies** (covered call, protective put, collar): add the stock leg's own delta — `share_quantity × 1.0` — to the net delta total; e.g. 100 shares plus one short 0.50-delta call is net delta ~+50 (long stock dominates), not ~-50 from the option leg alone. **0DTE legs** (a horizon expiring today, `dte_calendar == 0`) divide by zero in the standard Black-Scholes formulas if `T` is computed as calendar-days/365 — the engine's own `calculate_greeks()` raises on `T <= 0` for the same reason. Use the actual fraction of a year remaining until the contract's settlement cutoff (not whole calendar days), or say the calculation is unavailable once that cutoff has passed.

| Greek | Meaning (per share — multiply by 100 × contracts × long/short sign for $ exposure) |
|-------|---------|
| Delta | Change in option price per $1 move in underlying |
| Gamma | Delta's rate of change per $1 move |
| Theta | Daily time decay |
| Vega | Change in option price per 1-point IV change |
| Rho | Change in option price per 1% rate change |

### Step 5 — Simulate P/L
Max profit, max loss, breakeven(s), rough probability-of-profit band. An ASCII P/L diagram is a nice-to-have, not required — don't over-produce it for a quick question. **Exception — Calendar and Diagonal spreads**: their legs expire on different dates, so there is no single terminal intrinsic-value payoff to compute — the remaining long leg's value at the short leg's expiry depends on then-current spot and IV, not just intrinsic value. Don't state a fixed max profit or breakeven for these two; instead walk 2-3 spot/IV scenarios at the near-leg expiry and label them as scenario-dependent estimates, not exact figures. If reusing `engine/options/premium_calculator.py` for probability-of-profit, note its `probability_of_profit()` docstring says the `target_pct` parameter is "unused in the current implementation" — it returns the risk-neutral probability of expiring **ITM**, not the probability of profit past a premium-adjusted breakeven (an option can expire ITM and still lose money). Label that helper's output "probability ITM," compute an actual breakeven-based POP by hand if the user needs the real thing, and for multi-leg strategies compute POP over the strategy's own breakeven region, not a single leg's ITM probability.

### Step 6 — Strategy-specific walkthrough
Cover setup, max profit/loss, breakeven, Greeks, assignment risk, when to use / avoid, exit plan. Keep it to the strategy actually asked about — don't dump all 18 unless the user wants a comparison table.

### Step 7 — Earnings strategies
Fetch the earnings date if the engine/watchlist tooling has it available (check for an earnings-calendar source in `engine/` before assuming there is none). Flag IV-crush risk explicitly for any pre-earnings long-premium strategy (straddle/strangle), and IV-crush *benefit* for short-premium strategies (iron condor) — this is the single most common mistake retail options traders make and the original skill's IV-crush framing is worth keeping verbatim in spirit.

### Step 8 — Risk sizing
Position size against the user's stated risk tolerance (max loss × contracts <= risk budget), same logic as the original skill. Watch the contract multiplier: a `max_loss` computed by hand from `black_scholes_price()` (Step 3) is **per share**, so it must be multiplied by 100 before dividing into the risk budget — a $2 per-share debit is $200 of actual risk per contract, and skipping the multiplier recommends ~100x too many contracts. An `/options-signals/opportunity-board` candidate's own `max_loss` is already a dollar figure (don't multiply it again). This is advisory sizing for the user's own broker account discussion, not jarvis's own capital allocation — jarvis's own `$5K/instrument` cap and kill-switch live in `engine/config.py` / `.claude/rules/safety.md` and are not yours to recompute or override here. **Undefined-risk strategies** (naked short straddle/strangle, a net-short-call uncovered ratio spread, or any other short call position with no bought wing *and no covering stock*) have genuinely unbounded max loss, so `max loss × contracts <= budget` has no solution — but check for stock coverage before applying this test: a **covered call** (or a call ratio whose excess short calls are fully backed by owned shares) has no bought option wing yet is still bounded, because the shares supply the assignment and the combined stock+option position has a finite worst case at the underlying going to zero. Classify the *combined* stock-and-option payoff, not just whether an option wing exists, before calling something unbounded. don't substitute broker margin requirement or a stress-test number for max loss and quietly produce a contract count. Say plainly that no finite size satisfies a fixed dollar risk budget there, and that sizing is a margin/risk-tolerance question instead. **Exception**: an uncovered *put* ratio spread is not unbounded — the underlying can't go below zero, so its max loss is large but finite (compute it at the zero-price floor) and normal max-loss-based sizing still applies. **A calendar or diagonal can also be unbounded, depending on which leg is short-dated and which side (call/put)**: a "reverse" construction (long the near-term option, short the longer-dated one) leaves the position naked once the near leg expires and the far leg's hedge is gone. For a **reverse call calendar**, that naked far short call has genuinely unbounded upside loss, same as a naked short call. A **reverse put calendar** is different — the same zero-price floor that bounds any short put applies here too: once the near long put expires, the remaining naked far short put can lose at most its strike, offset by the **net premium across both legs of the whole calendar** (not just the short leg's own premium) — if the position was opened for a net debit, that debit *adds* to the max loss (`short_strike + net_debit` per share) rather than reducing it; if opened for a net credit, subtract that credit. Compute the bound from all opening cash flows, not the short leg alone, but it is still large-but-finite, so normal max-loss-based sizing still works for it. The standard calendar/diagonal construction (short the near leg, long the far leg as the hedge) doesn't have this problem at all since the hedge outlives the short. Classify which leg is short-dated, which side is short, and call vs. put before sizing a calendar/diagonal — don't assume every calendar/diagonal has Step 5's bounded, scenario-based payoff, and don't lump reverse put calendars in with the truly unbounded cases. Only net-short-call ratios, naked calls/straddles/strangles, and reverse **call** calendars/diagonals are truly unbounded.

### Step 9 — Output
A short markdown report: setup, P/L summary, Greeks, risk assessment, entry/exit/stop guidance, when-to-use vs avoid, and (if useful) an alternatives comparison table. Match the depth to the question — a one-line "what's a collar" question doesn't need Step 9's whole template; a "should I put this trade on" question does.
