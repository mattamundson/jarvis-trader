=== ARCHITECTURE & DESIGN ===

Position Correlation Monitoring Pipeline:
1. Config Layer: INSTRUMENT_CORRELATION_PAIRS (config.py)
2. Orchestrator Layer: PositionCorrelationMonitor tracks positions
3. Sizing Layer: get_max_contracts() enforces MNQ+MES → 1 contract rule
4. Portfolio Layer: GET /portfolio/risk exposes exposure to dashboard
5. Risk Layer: RiskManagerAgent includes correlation warning in LLM prompt

Data Flow:
  Position Update → PositionCorrelationMonitor.update_position()
  Size Calculation → get_max_contracts(symbol) returns 1 or 2
  Portfolio Check → GET /portfolio/risk shows reduction_active=true/false
  Risk Review → RiskManagerAgent detects pair, includes warning in prompt

Safety Guarantees:
  - Correlation rule is DETERMINISTIC (no LLM dependency)
  - Applied BEFORE order submission (sizing constraint)
  - SafetyLayer unchanged (no modifications to hardcoded checks)
  - Complementary to existing position_sizing.validate_size()
  - No breaking changes to existing MCL behavior

=== ORCHESTRATOR ANALYSIS ===

Current Structure:
- engine/orchestrator/multi_market.py (180 lines)
  * MultiMarketOrchestrator: main coordinator class
  * Manages lifecycle (start/stop), strategy cycles, P&L aggregation
  * Global singleton pattern: get_orchestrator(), set_orchestrator()
  * Responsibilities:
    - register(module): Register market modules (futures, options, etc)
    - start(): Connect all modules and begin strategy cycles
    - run_all_cycles(): Execute strategy cycle on all active modules
    - get_portfolio_summary(): Aggregate P&L and positions across markets
    - halt_all(reason): Emergency halt (triggered by risk checks)

- engine/orchestrator/correlation_monitor.py (54 lines)
  * CorrelationMonitor: directional exposure tracker
  * Tracks net long/short as % of capital (simple aggregation)
  * is_overexposed(): checks if total exposure > threshold
  * Current logic: DIRECTIONAL (net long/short), not PAIR correlation

- engine/orchestrator/capital_allocator.py (60 lines)
  * CapitalAllocator: dynamic capital rebalancing
  * Tracks performance history per market (rolling 30 days)
  * ramp_up(market): Increase allocation in 25% steps
  * Not involved in position sizing decisions

How Instruments Are Registered:
- MultiMarketOrchestrator._modules: dict[str, MarketModule]
- Each module has: market_name, is_enabled(), daily_target, capital_allocated
- Modules are NOT yet structured to return instrument-specific positions
- Need to trace through MarketModule interface to see position structure

Sizing Decision Locations:
- run_all_cycles() iterates modules, executes signals via execute_signal()
- No per-instrument max-contracts check in orchestrator
- Sizing likely happens in individual market module implementations
- Engine config (engine/config.py) has:
  * MAX_CONTRACTS_PER_INSTRUMENT = 2 (global limit)
  * MAX_OVERNIGHT_CONTRACTS = 1
  * No instrument-pair correlation logic

Existing Tests:
- engine/tests/test_orchestrator.py (fixture-based)
  * MockMarketModule for testing orchestrator lifecycle
  * Tests: register, connect, run_all_cycles, portfolio_summary, halt/resume
  * No existing correlation tests

Key Insight:
The orchestrator is MARKET-level, not INSTRUMENT-level. It coordinates
modules (futures, options, crypto) but doesn't directly manage MES/MNQ.
Correlation logic must:
1. Track individual instrument positions (MES, MNQ, MCL) across modules
2. Apply sizing rules based on instrument pairs when BOTH have open positions
3. Be applied BEFORE order submission (in position sizing calc, not orchestrator)
