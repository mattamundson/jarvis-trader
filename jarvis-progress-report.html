What JARVIS TRADER Does

JARVIS TRADER is a fully autonomous AI-powered trading system for micro futures (MCL, MNQ). It uses a 5-stage LLM pipeline where AI agents analyze markets, debate bull vs bear cases, make trading decisions, validate risk, and approve orders — all with a hardcoded safety layer that humans can never override. The system is currently in a 30-day paper trading validation phase that started April 2, 2026.

System Architecture

● Engine (FastAPI)

  • Port 8010 — Python 3.12, async
  • 90+ endpoints across 26 routers
  • 10 AI agents in 5-stage pipeline
  • SQLite for trades, decisions, P&L
  • APScheduler for watchlist scan, EOD, backups
  • Polygon.io + Finnhub market data
  • IB Gateway paper trading (port 4002)

● Dashboard (Next.js 15)

  • Port 3011 — TypeScript, Tailwind
  • 22 pages covering all trading aspects
  • WebSocket for real-time events
  • SWR polling at 5-30s intervals
  • Dark terminal aesthetic theme
  • Kill switch toggle with confirmation
  • Agent feed showing all 10 agent decisions

● Safety Layer (Hardcoded)

  • Kill switch: -2% daily / -10% drawdown
  • Max position: 5% of portfolio
  • Max contracts: 2 micro per instrument
  • Rate throttle: 10 orders/minute
  • Human approval: ALWAYS required
  • Port 4001 blocked: No live trading access
  • Tilt detection: Revenge trading prevention

● Learning System

  • Event capture: All decisions logged
  • Feedback loop: Outcomes to agent prompts
  • Pattern recognition: Signal correlation
  • Recommendations: Parameter tuning
  • Loss tracker: 3→0.5x, 5→0.25x, 7→halt
  • Database backup: Nightly at 23:30 UTC
  • 30-day retention: Automatic cleanup

Gap Analysis — What's Missing

The engine is built, the dashboard is running, the safety layer is bulletproof. But the system can't actually trade yet. Here's why.

Critical Gap

No Trade Approval UI

The pipeline produces signals and requires human approval (REQUIRE_HUMAN_APPROVAL=True), but the dashboard has zero approve/reject buttons. Pending signals appear in the queue on /paper but Matt can't act on them. This is the #1 blocker for paper trading.

Engine: Endpoint exists Dashboard: 0% built
Critical Gap

Scheduler Doesn't Execute Trades

The watchlist scanner runs every 30 minutes, calls the full 5-stage pipeline, and gets trade decisions — then logs them and does nothing. No code path connects pipeline output to order submission. This is a ~20 line fix with proper safety gates.

~20 lines of code Safety gates needed
High Priority

IB Gateway Client ID Conflict

IBKR data connection fails because client ID 10 is already in use (likely ThinkorSwim Desktop). The paper connector works fine independently. Fix: change IBKR_CLIENT_ID in .env from 100 to a unique value, or ensure no other client is connected.

Config change Non-blocking (Polygon fallback)
High Priority

ALLOW_PAPER_SIMULATED_ORDERS = False

Even with all code in place, the config flag that permits paper order simulation is currently set to False. Must be set to True in .env and the engine restarted to enable simulated fills during paper validation.

Config change in .env Engine restart required
Medium Priority

WebSocket Not Active on Dashboard

The WebSocket infrastructure exists on both sides (engine /ws/events, dashboard useWebSocket hook) but isn't actively used on the home page. The dashboard falls back to SWR polling (5-30s intervals). Real-time is better for live trading.

Hook exists Wire into key components
Medium Priority

NODE_ENV=production System-Wide

Windows has NODE_ENV=production set globally, causing Next.js dev server warnings and potential optimization conflicts. The zombie node process on port 3010 also needs clearing (access denied). A system reboot would fix both.

System env fix Reboot clears zombies

The Vision: How It All Works Together

Every 30 minutes during market hours:
1. Scheduler triggers watchlist scan for MCL and MNQ
2. Pipeline Stage 1: Four AI analysts examine price action, news, sentiment, fundamentals
3. Pipeline Stage 2: Bull and Bear researchers debate the thesis
4. Pipeline Stage 3: Trader agent synthesizes a decision (buy/sell/hold)
5. Pipeline Stage 4: Risk Manager validates against safety limits (can VETO)
6. Pipeline Stage 5: Fund Manager checks portfolio fit
7. If trade signal: pushed to pending approval queue + WhatsApp alert to Matt
8. Matt reviews on dashboard, clicks Approve or Reject
9. Approved trade routes through SafetyLayer → OrderRouter → Paper fill simulation
10. P&L tracked, learning system records outcome, agents improve over time

After 30 days: If validation gates pass (PF ≥ 2.0, Sharpe ≥ 1.5, WR ≥ 55%, DD ≤ 15%), the system graduates to Phase 3: live trading with real capital at reduced position sizes.
