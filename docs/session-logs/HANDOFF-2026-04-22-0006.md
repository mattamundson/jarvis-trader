## §A. Session Insights — Patterns Worth Carrying Forward

Put these above the timeline because they change how you READ the timeline.

### Pattern 1: "Static cutoff tuned to a past reality" is a whole class of latent bug

Three separate patches this session were all symptoms of the same root cause:
- `6f45fa7` (prior): /health timeout 60s → 180s
- `54a16e6`: /health timeout 180s → 360s
- `a081897`: uptime cycle-detector 60000ms → elapsed-time-bound

Each looked standalone. Each was a correct local fix. But each was caused by the same underlying assumption ("startup is fast") being encoded in another place and only surfacing when the previous patch removed the more-conservative gate.

**The meta-lesson:** When you relax a conservative boundary, you expose every OTHER boundary that silently relied on that conservatism. Before patching a threshold, grep the whole file (and ideally the whole repo) for related thresholds that might break together. Sibling assumptions often fail in sequence — one at a time as each new ceiling is raised — making each fix feel urgent even though they share a root cause.

The proper fix arrived in `890a04d` (P1.8 partial): **remove the slow thing from the critical path**, don't keep patching the detectors that notice the slowness. Once the scanner defers its first scan by 60s, uvicorn binds in ~15s and all three ps1 thresholds become trivially satisfied.

### Pattern 3: Stale memory files create false-alarm work

Twice this session I almost did work that was already done:
- `project_mes_outcome_backfill_bug.md` was marked "flagged" when the fix was already in commit `1c89343`
- Task #27 (main.py forward_recorder refactor) appeared in_progress when commit `28b420c` had already closed it

Both were caught by grepping before acting. Both would have been *easy* to not catch — I almost dove into implementing the fixes before verifying the current state.

**The meta-lesson:** Before acting on any "known issue" or open task:
1. Grep the commit log for the symptom (`git log --all --grep="<keyword>"`)
2. Read the current state of the named file/function, not the state described in the memory
3. If the memory claims a bug exists, WRITE a failing test FIRST to prove the bug exists; if the test passes (no bug), update the memory and move on

Applied rigorously, this saves the next session from doing 30-60 min of work that was already done.

**Commit:** `a081897`
**Alternatives considered:**
- Raise static cutoff 60000ms → 420000ms (matching /health ceiling + margin) → rejected (still future-stale; same class of bug)

**Chosen:** elapsed-time-bound because it's self-scaling. The invariant "a fresh restart's pm_uptime cannot exceed the script's own runtime" is true regardless of how fast or slow startup gets.

**Rollback:** Trivial. But don't — the new check is strictly more correct.
