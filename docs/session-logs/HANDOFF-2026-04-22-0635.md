## 6. Key decisions made

### Architecture
- **Separate `mcl_meanrev_regime_search.py` from `mcl_meanrev_search.py`** — V2 (Bollinger+RSI+regime filter) is a distinct `_run()` from V1 (Bollinger only, no regime). Refactoring V1 would have mutated existing validation artifacts; creating a sibling module is cheaper and preserves baseline.
- **Family-based dispatch stays the pattern** — 4 families now: `trend` (MES), `meanrev` (MCL V1), `breakout` (MNQ), `meanrev_regime` (MCL V2). One more `elif` branch per validator per new strategy. Clean seam, no dispatcher duplication.
- **`get_tick_price()` intentionally skips TV** — documented as Tier-0-skip; opposite orientation from `get_current_price()` which uses TV Tier 0 for bars. Comment in code makes the asymmetry explicit.
- **Tolerant `reset_index`** — added a column-presence check rather than always `reset_index(drop=True)` — the latter would have broken cases where timestamp is the index only.

### Parameter values
- **MCL bbwidth gate v2 test params (the canonical config)**:
  ```json
  {"bb_period":20, "bb_std":2.0, "rsi_long":30.0, "rsi_short":70.0,
   "stop_atr_mult":1.5, "regime_filter_mode":"bbwidth",
   "regime_filter_bbwidth_pct":40.0, "regime_filter_adx_threshold":20.0}
  ```
- **MNQ breakout SHORT-only canonical config**:
  ```json
  {"donchian_period":20, "vol_ma_period":20, "vol_mult":1.0,
   "stop_atr_mult":2.0, "short_only":true}
  ```
- **Data range used**: `2024-06-01 → 2026-03-27` for all validators (matches cache).
- **Gate v2 CORE ceiling at $10K** = 6.0% MC DD; **$50K** moves MNQ under it.
- **Validator thresholds** (don't change without re-memory):
  - Rolling WFO: STRONG median≥1.5 & pct_profitable≥70%; MODERATE ≥1.3 & ≥60%; WEAK ≥1.1 & ≥50%.
  - Fixed-params: STRONG all_profitable & min_pf≥1.30; MODERATE all_profitable & min_pf≥1.00; MIXED pct_profitable≥70%.
  - ALT accepts MODERATE or STRONG.

## 13. Gate v2 math primer

This section exists so the next AI doesn't have to reverse-engineer the validator to understand *why* a strategy with a raw PF of 1.52 can end up with an MBB lower-bound of 1.07.

### 13.1 Why dual-pathway (CORE vs ALT)

Gate v2 replaces the previous single-threshold gate because two classes of strategies exist:

- **Rich-sample strategies** (lots of trades, distribution well-sampled): bootstrap PF CI is a tight estimate, and we can demand it holds above 1.10.
- **Sparse-sample strategies** (few trades, heavy tails): bootstrap CI is dominated by sampling noise and a 1.10 floor is unachievable even for strategies with genuine multi-window edge. For these, we admit the strategy if *multiple orthogonal lenses* agree it has edge — temporal stability, cost robustness, selection-bias-adjusted Sharpe, and DD.

A strategy PASSES if *either* pathway is satisfied. DSR (deflated Sharpe ratio) is the only criterion required on both paths because it cannot be relaxed by sample-size — if a strategy's Sharpe doesn't survive multiple-testing correction, no lens adjustment helps.

### 13.2 The 9 criteria (4 CORE + 5 ALT) in detail

| Criterion | Threshold | Meaning | Why this threshold |
|---|---|---|---|
| **mbb_pf_ci_lower** (CORE) | ≥ 1.10 | 2.5th percentile of 1000 moving-block-bootstrap PFs | Leaves 10% margin above 1.0 so CI lower-bound sampling noise doesn't misfire |
| **p_positive_edge** (CORE) | ≥ 0.95 | Fraction of IID bootstrap resamples with PF > 1 | Strong evidence (≥ 95% of parallel worlds) that strategy is profitable, not noise |
| **mc_95th_dd_pct** (CORE) | ≤ 6.0% | 95th percentile of MC permutation max-DD, as % of initial capital | $600 on $10K is ~60% of $5K/instrument kill-switch, so 6% is the prudent ceiling |
| **dsr** (both) | ≥ 0.10 CORE / ≥ 0.30 ALT | Bailey-Lopez deflated Sharpe p-value proxy after multi-testing adjust | Below 0.10 = selection-bias-indistinguishable; ALT raises to 0.30 because it relaxes other evidence |
| **rolling_wfo_verdict** (ALT) | ∈ {MODERATE, STRONG} | Rolling walk-forward test PF median / % profitable | MODERATE = median PF ≥ 1.3 AND ≥ 60% windows profitable |
| **fixed_params_min_pf** (ALT) | ≥ 1.20 | Min PF across 4 non-overlapping 6-month segments | If the worst contiguous 6mo segment still profits at 1.20, the edge is temporally stable |
| **cost_survives_through** (ALT) | ≥ realistic | Ordinal: optimistic < baseline < realistic < stressed < catastrophic | Realistic = 2× commission + 2× slippage; if PF ≥ 1 at that level, strategy tolerates real execution |
| **mc_95th_dd_pct** (ALT) | ≤ 7.0% | Same metric as CORE, looser ceiling | ALT concedes 1pp of DD tolerance given the stronger supplementary evidence |

### 13.3 Why MBB PF CI differs from IID PF CI

Look at MNQ's block bootstrap result (from the actual JSON):

| | IID bootstrap | Moving-block bootstrap |
|---|---|---|
| Median PF | 1.518 | 1.545 |
| CI 95 lower | 1.032 | **1.070** |
| CI 95 upper | 2.188 | 2.107 |
| Block size | — | 15 trades |

MBB is narrower than IID on both ends — because serial correlation means trades aren't independent. If you win today you're more likely to win tomorrow (trend clustering); IID resampling destroys that correlation and *widens* the tails. MBB preserves chunks of consecutive trades (size ≈ √N), so its tails reflect realistic regime clustering.

The gate uses MBB because financial returns are serially correlated and IID overstates CI width. A strategy that passes the narrower MBB test is robust to the realistic correlation structure.

### 13.4 Why MC DD is % of initial_capital (and why $10K vs $50K matters so much)

`bootstrap_max_dd` permutes the realized trade sequence 10,000 times and for each permutation computes the max drawdown as a % of initial capital. The 95th percentile is the DD you'd expect to exceed in only 5% of alternate histories.

**MNQ's 95th DD scales inversely with capital:**
- At $10K: 95th DD = **21.97%** → $2,197 cash drawdown.
- At $50K: 95th DD = **5.29%** → still $2,645 cash drawdown (proportional ~1:1 to position size).

The ratio is close to 1:5 because MNQ has fixed dollar-per-tick risk independent of account size. Larger account = same absolute DD = smaller %.

**MCL bbwidth does NOT scale the same way** — MC DD was already 4.76% at $10K. Re-running at $50K would yield ~0.95% DD, which doesn't unlock anything. MCL's remaining failures (`fixed_params_min_pf=0.397`, `rolling_wfo=WEAK`) are about the *quality of the edge across time*, not account size.

This is the single most important distinction for the next session: **if a strategy fails on MC DD only, raise capital and retry; if it fails on temporal lenses, capital doesn't help.**

### 13.5 DSR (deflated Sharpe ratio) intuition

Standard Sharpe is biased upward when you grid-search — the winning config is not just the best strategy but also the one with the luckiest draw. DSR (Bailey & Lopez de Prado 2014) applies a multiple-testing correction:

```
DSR = Φ( (SR_observed - E[max SR | N_trials, 0 true edge]) / σ_SR )
```

- `E[max SR]` = expected max Sharpe if *all* trials had zero edge. Larger N_trials → larger correction.
- `σ_SR` = standard error of SR.

For our strategies, `n_trials=1` (single config being validated post-hoc, not grid-searched in-validator), so `E[max]=0` and DSR is just Φ(SR/σ_SR). This gives us DSR = 1.0 for MNQ and MCL bbwidth — they're both very far from noise.

**When DSR would drop:** if we validated multiple grid-ranks simultaneously (e.g. "top 10 MES trend combos"), `n_trials=10` and each combo's DSR would be lower because *one* of them was expected to look great by chance. This is why we validate a single config at a time, selected by criteria other than raw PF.

## 15. Validator dispatcher architecture

All 3 ALT validators share the same dispatch pattern. The clean seam means adding a new strategy family requires exactly one `elif` branch per validator (three total) + one results file.

### 15.1 The `_run()` contract

Every research harness module exports:

```python
def _run(df: pd.DataFrame, *params, spec: dict) -> dict:
    """Returns dict with keys:
      total_trades: int
      pf: float                 # profit factor, 999.0 sentinel if no losses
      wr: float                 # win rate %, 0-100
      net_pnl: float            # USD
      ret_pct: float            # % of initial capital
      trades: list[dict]        # per-trade records (for bootstrap/MC)
      avg_win: float
      avg_loss: float
      skipped: bool             # optional — if True, validator drops window
    """
```

The `spec` dict carries per-symbol constants:
```python
{
    "multiplier": float,      # $ per point
    "tick_size": float,       # minimum price increment
    "commission": float,      # $ per side per contract
    "slippage_ticks": int,    # realistic slippage on fill
}
```

### 15.2 Per-validator dispatch pattern (all 3 look like this)

```python

    default_rf = _ENGINE / "scripts" / f"{symbol.lower()}_trend_search_results.json"
```

## 17. Code-level decisions with snippets

### 17.1 Edge-detector pattern (Track 1a fix)

The bug: on monotone-trend test data (ADX climbs to 25 and stays), `newly_strong = strong & ~strong.shift(1)` fires only once — the first bar strong becomes True. But the original test expected entries throughout.

The fix: we actually *want* the one-shot behavior — but the test data needs to cycle the condition off/on. Alternative: use a compound condition that naturally cycles (bull vs bear bias).

Final code in `engine/backtest/adx_ema_signals.py`:

```python
strong_bull = strong & bull_bias
strong_bear = strong & bear_bias
enter_long = strong_bull & ~strong_bull.shift(1, fill_value=False)
enter_short = strong_bear & ~strong_bear.shift(1, fill_value=False)
exit_trigger = weak
```

This fires an entry *exactly* on the bar a compound condition becomes True — cleaner than the old "monitor crossover of a single scalar" approach. Works equivalently for trend and mean-reversion generators.

### 17.2 Tolerant `reset_index` (post-plan 2 fix)

### 17.3 Regime gate helper (Track 4)

In `engine/backtest/meanrev_signals.py`:

```python
def _build_regime_gate(
    df: pd.DataFrame,
    mode: str,
    bbwidth_pct: float,
    bbwidth_lookback: int,
    adx_threshold: float,
    keltner_atr_mult: float,
) -> pd.Series:
    """Return a boolean Series — True means 'allow entries this bar'.
    Default mode='none' returns all-True (no suppression).
    """
    if mode == "none":
        return pd.Series(True, index=df.index)
    if mode == "adx":
        adx = compute_adx(df, period=14)
        return adx < adx_threshold   # Trending regime suppresses mean-rev
    if mode == "bbwidth":
        width = bb_upper - bb_lower
        rank = width.rolling(bbwidth_lookback).rank(pct=True) * 100
        return rank <= bbwidth_pct   # Low-vol regime only
    if mode == "keltner":
        kc_upper, kc_mid, kc_lower = keltner_channels(df, keltner_atr_mult)
        # Skip when both BB and KC are simultaneously breached (extreme-extreme)
        return ~((df.high > kc_upper) & (df.high > bb_upper))
    raise ValueError(f"unknown regime_filter_mode: {mode}")
```

**Design note:** the helper returns an "allow" mask, not a "suppress" mask. The call site ANDs it into the existing entry condition:

```python
entry_mask = entry_mask & _build_regime_gate(df, mode, ...)
```

This means the default `mode="none"` is a pure no-op (all-True), which preserves backward compat with the 15 pre-existing tests.

### 19.2 999 sentinel for "no losses" PF

`_run()` returns `pf=999.0` when `gross_loss == 0`. All validators treat this as `inf` for percentile/filtering purposes, but don't include it in mean/median. If a verdict function uses a naive `min(pfs)`, the 999 pollutes.

## 20. Research journal — "why we tried what"

This section captures the *reasoning trace* behind decisions — more useful than just the outcome.

### 20.1 Why Phase D/E strategies were unlikely to pass

The original research memo framed 3 strategies (ADX-EMA, RSI-breakout, ATR-channel) as "Phase D/E strategy matrix" candidates. Prior memory `project_phase_d_strategy_comparison.md` already knew SMA(50,200,2.0) dominated Donchian on MES 1h. So there was a reasonable prior that these 3 would also fail to beat SMA — but the test was cheap and required for breadth.

The *real* SMA baseline is PF 1.895 / Sharpe 3.474 / n=35 on the fixed champion. For any of the 3 new strategies to displace SMA, it would need to beat that on test-window PF AND have WFE ≥ 0.5 AND n ≥ 20. None came close. Accepting this as confirmation that SMA trend is robustly the best-fit for MES 1h, rather than wasted effort, is the right read.

### 20.2 Why MNQ's failure surprised less than MCL's

Pre-session memory `project_mnq_breakout_first_pass_edge_found.md` already knew MNQ SHORT-only don=20 had p_positive_edge=0.98 and passed the PF≥1.30 smoke gate but failed CORE at $10K with 22% DD. The expected move was that $50K would rescue DD (since DD % scales inversely with account). That's exactly what happened — DD dropped 22% → 5.29%. The *unexpected* residual was MBB PF CI lower stuck at 1.07 and fixed_params_min_pf stuck at 1.19. Both are sample-size-coupled; $50K doesn't help with those, only more trades do.

MCL was the actual research novelty — the bbwidth filter finally producing a PF > 1 result was genuinely new information. But the specific failure mode (seg 3 at PF 0.40) was not predictable from the smoke result.

### 20.3 Why we used `regime_filter_bbwidth_pct=40.0`

The smoke script sweeps `{bbwidth=40, adx<20, keltner}` as three filter variants. 40% was a reasonable "bottom 40% vol regime only" choice — not grid-searched. For future iteration, a sweep over `{30, 35, 40, 45, 50}` would tighten or loosen; 30 would likely cut trades further at probably-higher PF, but thin out the sample.

**Do not grid-search bbwidth_pct in a CORE validator run without also adjusting DSR trial count** — that would be exactly the selection-bias scenario DSR corrects for.

### 20.4 Why cost_sweep survived STRESSED but not CATASTROPHIC

MCL bbwidth at catastrophic (8× comm + 5× slip) got PF 0.77 — below break-even. At stressed (4× comm + 3× slip), PF 1.08 — barely above. The catastrophic scenario uses $6.80 commission per side + 5 tick slippage = ~$11 per round-trip. Given MCL's $10 tick value, that's 1.1 ticks of pure cost. On a strategy with +0.156 pts expectancy (from smoke), that's half the edge consumed before P&L.

MNQ breakout survives catastrophic because its edge is much larger (16.86 pts per trade, ~$34 on MNQ multiplier) and its cost is $1.24 round-trip baseline. Even 8× = $10 is <30% of expectancy.

### 20.5 Why separate `mcl_meanrev_regime_search.py` from the V1 search

Tempting to refactor V1 to accept regime_filter_mode with default "none". BUT: the V1 validation artifacts in `validation_reports/` were produced with specific `_run()` behavior. Refactoring the V1 module would silently change what those artifacts mean if someone re-ran them. Creating a sibling module at the file-boundary is the safer archaeological choice — V1 stays frozen, V2 is additive.

This echoes the `feedback_rolling_wfo_overfitting.md` lesson: preserve prior baselines, don't mutate them to fit current intuition.

### 20.6 Why we didn't tune `regime_filter_bbwidth_pct` to pass the gate

Strong temptation: sweep `bbwidth_pct ∈ {30, 35, 40, 45, 50}`, find the value that minimizes seg 3 loss, declare PASS. This is **textbook overfitting**. Gate v2's `fixed_params_temporal_validator` explicitly exists to catch this — any tuning-to-fit would fail the "fixed" part of fixed-params. If we MUST iterate, the honest move is:
1. Note the hypothesis (e.g. "30% is tighter")
2. Run on a held-out 2026-Q2 data slice only (if/when it exists)
3. Decide on that slice alone

Until held-out data exists, the bbwidth=40 result stands as-is.

## 22. Statistical intuition for the next AI

### 22.1 "Sample-size-coupled" vs "temporal-instability" — mental model

- **Sample-size-coupled failures**: MBB PF CI lower, p_positive_edge, fixed_params_min_pf (when close to threshold). These narrow as N trades grows — shadow-mode accumulation is the mechanical fix.
- **Temporal-instability failures**: fixed_params_min_pf (when far below threshold because of a specific bad segment), rolling_wfo (WEAK verdict). These are structural — more trades of the *same* type won't help if the strategy has a known weak regime. The only fixes are (a) identify a priori filter for that regime (high overfitting risk), or (b) accept the strategy's weak-regime behavior as a known risk.

**Quick test**: is the gap small (miss by <10% of threshold) and is p_positive_edge > 0.95? Sample-size-coupled. Is fixed_params_min_pf < 0.8 or rolling_wfo WEAK? Temporal-instability.

### 22.2 Block bootstrap block size

`bootstrap_block.block_size` is automatically set to `ceil(sqrt(n_trades))`:
- MNQ n=219 → block=15
- MCL n=52 → block=8

This is the "square-root rule" for block bootstrap serial-correlation correction. If you see block_size=1, IID and MBB will give identical results (and the strategy has no meaningful serial correlation).

### 22.3 DSR at 1.0 is not a green flag by itself

All three strategies this session had `dsr=1.0`. That's because `n_trials=1` (single post-hoc config). DSR is load-bearing when validating *grid-search winners* because it corrects for the selection bias of picking the best combo. For post-hoc validation of a specific config, DSR reduces to the raw Sharpe significance. It's still a useful floor but not a discriminator.

**Rule**: DSR is most informative on grid-search validation, least informative on single-config validation.

### 22.4 The "one criterion away" illusion

MNQ at $50K is "one criterion away" from CORE PASS (MBB lower 1.07 vs 1.10) and "one criterion away" from ALT PASS (fixed_params min 1.19 vs 1.20). Tempting to declare "basically passing."

Reality check: both those criteria are statistical lower-bounds. MBB CI lower is the 2.5th percentile — being at 1.07 vs 1.10 means 2.5% of alternate-world PFs fall below 1.07 and 2.5% fall below 1.10. The gap between those is tiny compared to the uncertainty in the estimate itself (confidence on a confidence bound).

**The gate's job is to enforce a firm floor, not negotiate.** If the user wants to ship MNQ at $50K despite the miss, that's a Tier-3 decision — but don't weaken the gate to rubber-stamp it.

### 22.5 Why MBB CI is narrower upper than IID

Intuition: real trades have positive serial correlation (winning streaks, losing streaks cluster). IID resampling breaks those clusters, so the reconstructed distribution has more variance on both ends. MBB preserves clusters, so the tails compress — streaks that actually happened are reflected, improbable streaks that IID would generate are not.

For a strategy with low serial correlation (rare for financial strategies), MBB ≈ IID. For a strategy with high serial correlation (typical for trend/breakout), MBB is tighter. The gate uses MBB because financial markets are serially correlated.

### 22.6 `p_positive_edge` failing means the strategy barely has an edge

MCL bbwidth's `p_positive_edge = 0.884` means 11.6% of bootstrap resamples would show a losing strategy. That's uncomfortably close to the 20% tail where we'd say "no edge distinguishable from noise." Compare MNQ's 0.983 — only 1.7% of resamples lose, a strong signal.

**Rule of thumb**: if `p_positive_edge < 0.90`, treat the strategy as "edge suspected but not confirmed" and require unusually strong temporal-stability evidence. MCL bbwidth has neither, so the double-FAIL makes sense.

### 22.7 When the gate passes a strategy, what does it mean?

A gate v2 PASS via CORE: we have strong statistical evidence (MBB CI, p_edge, DSR) that the edge is real AND the DD profile is tolerable for a $10K account. Shadow-mode would still be required before live trading — gate v2 is *necessary*, not *sufficient*.

A gate v2 PASS via ALT: we have less statistical evidence but strong multi-lens confirmation (temporal, cost, selection-bias-adjusted). This is appropriate when sample size is inherently small (e.g. a weekly-bar strategy or a heavily filtered hourly strategy) and we cannot wait for N=200 trades.

No strategy has passed gate v2 on this codebase as of `ea58450`. The current live MES SMA champion passes gate v1 (the simpler bootstrap PF CI ≥ 1.10 test) but not gate v2 (which is tighter).
