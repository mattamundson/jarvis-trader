## 5. Blockers Discovered

### Blocker #1 — Bull/Bear researcher interface bug (HIGHEST PRIORITY)
**Source**: `engine/logs/engine-error.log` lines from 11:15:40 CDT:
```
2026-04-10 11:15:40 [WARNING] agents.debate: [Debate] _rebuttal (BULL) failed 
  (Agent BullResearcherAgent exposes no callable LLM interface 
   (_call_llm, call_llm, _client, client).)

2026-04-10 11:15:40 [WARNING] agents.debate: [Debate] _rebuttal (BEAR) failed 
  (Agent BearResearcherAgent exposes no callable LLM interface 
   (_call_llm, call_llm, _client, client).)
```

**The error comes from** `engine/agents/debate.py:908`:
```python
raise RuntimeError(
    f"Agent {type(agent).__name__} exposes no callable LLM interface "
    "(_call_llm, call_llm, _client, client)."
)
```

**But the source code CLEARLY has these methods**:
- `engine/agents/bull_researcher.py:167` — `async def call_llm(self, prompt: str) -> str:`
- `engine/agents/bull_researcher.py:301` — `async def _call_llm(self, prompt: str) -> str:`
- Same for `bear_researcher.py`

**Hypotheses for why the check fails at runtime**:
1. **Class identity issue** — The debate orchestrator may be holding an instance whose `type(agent).__name__` is `"BullResearcherAgent"` (so the class name matches) but isn't actually the class that has `call_llm`. Could be dual import paths creating two different classes.
2. **Callability check logic** — The interface check at `debate.py:908` probably iterates through `["_call_llm", "call_llm", "_client", "client"]` calling something like `asyncio.iscoroutinefunction(getattr(agent, name, None))`. If the getattr succeeds but the check uses a strict test that fails for wrapped methods (decorators, functools.wraps, etc.), the whole check returns False.
3. **Initialization order** — Maybe the researcher instances are constructed in a way that shadows `call_llm` with an attribute (e.g., `self.call_llm = some_wrapper` that doesn't satisfy the check).
4. **Recent refactor** — Commit `8d62523` added 173 lines to debate.py. Did any of those touch the `_rebuttal` helper or the interface check at line 908? I didn't read that section yet.

**The B1 defensive guard SHOULD be catching this** but isn't. Commit `8d62523` specifically added this at `debate.py` (~lines 429-446):
```python
# B1 defensive belt (2026-04-10): if both scores collapsed to zero
# without an upstream failure path setting scoring_failed, the
# debate is silently producing INCONCLUSIVE → forced HOLD downstream
# at pipeline.py:662. Catch the regression and flag it so the
# pipeline gate falls through to the trader instead of forcing HOLD.
if (
    bull_score == 0
    and bear_score == 0
    and not result.scoring_failed
):
    logger.warning(
        "[Debate] %s — both scores zero with no upstream failure flag; "
        "marking scoring_failed to bypass forced HOLD at pipeline gate",
        symbol,
    )
    result.scoring_failed = True
```

**But the live data shows**: `reasoning="Debate inconclusive (score=+0.000). Bull and bear cases are too evenly matched — holding."` — this message is NOT the B1 guard's warning. The debate is producing a score of `+0.000` (not bull=0,bear=0 necessarily) and going through a DIFFERENT code path that generates this "evenly matched" reasoning. The guard must not be firing because either:
- The score is `0.000` because `bull_score == bear_score` (both 5, not both 0)
- OR the guard runs but `scoring_failed=True` doesn't actually bypass the forced HOLD at `pipeline.py:662`

**Fix path** (next session):
1. Read `engine/agents/debate.py:845-920` (the `_rebuttal` function and the interface check)
2. Add diagnostic logging to print `type(agent).__name__`, `dir(agent)`, and `getattr(agent, "call_llm", None)` before the interface check
3. Add a test that constructs a real BullResearcherAgent and runs the interface check — it should pass
4. If the test passes but production fails, it's an initialization/injection issue
5. Consider reverting commit `8d62523`'s debate.py changes if the bug is in the new advisor-consult code path
