## 5. Blockers discovered (need resolution before MES goes live)

Ranked by severity. All three must clear before even a 1-contract MES live flip is safe.

### BLOCKER 1 — No broker-side STP orders anywhere in the codebase (HIGHEST RISK)

`engine/backtest/trend_signals.py:10-12` explicitly says:
> `Stop: initial stop = entry - trail_mult × ATR(14) at entry bar. (Static at entry; full trailing stop requires Backtester enhancement.)`

The "trailing stop" you think you have is **static**, set at entry bar only, never updated.

Worse: `grep -rn "STP" engine/execution/ engine/agents/ engine/trader/ engine/pipeline/` returns **zero matches**. The trader agent computes `stop_price` and writes it to `paper_trades.stop_loss` for logging. Nothing places a STP order on IBKR. `ib_gateway.place_paper_order()` at `engine/execution/ib_gateway.py:510-518` supports `order_type="STP"` but no caller ever invokes that path.

**Consequence**: engine crash or network disconnect mid-trade = position runs naked until you flatten manually. With pm2 restart count at 558, this is not a hypothetical.

**Fix sketch**: after entry fill confirmed, submit a child STP order via `place_paper_order(order_type="STP", aux_price=stop_price, parent_order_id=<entry_id>)`. Must be done on the IBKR-server side, not in Python state.

### BLOCKER 2 — Position-size gate rejects every MES order

`engine/risk/safety_layer.py:608-613` checks `estimated_value / portfolio_equity <= MAX_POSITION_SIZE_PCT (0.10)`. 1 MES contract at ~$7,130 × $5 multiplier = ~$35,650 notional. Against `INITIAL_CAPITAL=10000` in `.env`, this is 356% of equity → reject.

`_check_order_value_limits` has no futures-specific branch — it treats notional as equity exposure, not margin requirement.

**Fix options**:
(a) Sync `portfolio_equity` from IBKR via `sync_from_broker()` so real IBKR paper equity (~$1M typical) is used
(b) Add a `if symbol in FUTURES_SYMBOLS: use margin_requirement(symbol)` branch
(c) Both

Recommendation: (a) first (smaller change), then (b) as defense in depth.

### BLOCKER 3 — Paper-trade accumulation halted

With `WATCHLIST_SCAN_ENABLED=false`, MES has accumulated only 3 genuine paper trades since 2026-04-10 (now 4 with the anomalous one from today — see "anomalous paper trade" in §3). This is not sufficient to validate the strategy's behavior under current market regime before live flip.

**Fix**: re-enable scanner (already-vetted per §4.1). Then observe paper_trades accumulation rate for 5-10 trading days. Expected ~2-4 MES trades/week based on SMA(50, 200) crossover frequency on 1h bars.

### Minor blockers (should fix but not show-stopper)

- **`REQUIRE_HUMAN_APPROVAL=True` + `LIVE_TRADING_ENABLED=True` blocks ALL orders** with no approval-surface code path. Untested combined state. At live-flip time, must choose: autonomous (`REQUIRE_HUMAN_APPROVAL=False`) or build approval surface first.

## 6. Key decisions made (with tradeoffs)

### Decision 1 — Disable (not delete) duplicate scheduled task
Disabled `JarvisDiscordBookmarkRefresh` while keeping `JarvisTrader_DiscordBookmarks_Refresh`. Reversible via `schtasks /change /tn ... /enable`. Tradeoff: keeping both enabled is not dangerous after the UTF-8 BOM fix (they'd just race harmlessly on file writes and last-write-wins), but single-task is cleaner and matches the namespacing convention of other `JarvisTrader_*` tasks.

### Decision 2 — UTF-8 BOM rule for all PowerShell scripts invoked via Task Scheduler
**Rule**: any `.ps1` file invoked by Windows Task Scheduler's default `powershell.exe` (PowerShell 5.1) must be saved as **UTF-8 WITH BOM** if it contains any non-ASCII character. Tradeoff: BOM is invisible in editors, but some Unix tools (and older Git configs) can flag its presence. Acceptable because these scripts are Windows-specific.

### Decision 3 — Commit `dce-nightly.ps1` but do NOT push `refresh_discord_bookmarks.ps1`
`dce-nightly.ps1` is in the jarvis-trader repo → committed + pushed (`597fa26`). `refresh_discord_bookmarks.ps1` is in `C:\Users\mattm\discord-export\` → lives in the newly-initialized discord-export local repo (commit `6d23bc3`). Tradeoff: splits version-control across two repos, but respects the existing directory boundary and avoids pulling Obsidian-specific pipeline code into the trader repo.

### Decision 4 — Local-only git for `discord-export/` (no remote)
Reason: directory has 100+ MB of Discord JSON exports + images. A GitHub remote would need LFS or a private repo. Deferred that decision to user. Tradeoff: local-only means a disk loss = commit history gone. Acceptable because the scripts are small and the critical fix (UTF-8 BOM) is also mirrored in this handoff document.

### Decision 5 — Explicit file staging, not `git add -A`

Only fixed in `C:\Users\mattm\discord-export\discord_to_obsidian.py` because that was within the immediate Discord-pipeline scope. The jarvis-trader repo likely has similar deprecation warnings (didn't grep) but fixing them requires test re-run and could touch many files. Deferred.
