#### 4f. Wrote the hook script

Full content reproduced in Section 2. Design characteristics:
- **Three modes** routed via `$1`: `start`, `stop`, `list`
- **`set -eu`** — strict mode. No `set -o pipefail` because hook chain should fail open; pipe-ordering issues should not break session.
- **Atomic write via `mktemp` + `mv`** on every manifest mutation
- **Stale-eviction on every invocation** — not a background sweeper; costs O(n) per call where n = total sessions ever seen in the last 24h (bounded at maybe 3-5 on this machine)

- **`session_id` is the only identity** — no PID, no TTY, no hostname. The session_id is stable for the life of a Claude Code session.
- **Branch detection via `git -C "$hook_cwd" rev-parse --abbrev-ref HEAD`** — robust because `-C` doesn't require the shell's cwd to match; empty string on non-repos
- **Timestamp stored twice**: ISO-8601 UTC string (`started`) for human readability + Unix epoch (`started_epoch`) for cutoff math
- **Peer-report emission** uses `jq -n --arg msg "$msg" '{systemMessage: $msg}'` to build well-formed JSON that Claude Code injects as a system message

#### `C:\Users\mattm\.claude\hooks\session_manifest.sh` (NEW)

**Size:** 5,184 bytes · **Permissions:** 755 (executable) · **Encoding:** UTF-8 LF · **Shebang:** `#!/usr/bin/env bash`

**Purpose:** Bash script that manages the session manifest at `~/.claude/session_manifest.json`. Invoked by Claude Code hooks at session boundaries; also callable manually for inspection.

**Full content** (annotated):

```bash
#!/usr/bin/env bash
# Line 1-21: Header docblock explaining usage, stdin format, and design notes.
# Key design decisions documented in the header itself so future maintainers
# don't need to reverse-engineer intent.

set -eu
# Strict mode: fail on any unbound variable or non-zero exit.
# NOT using `set -o pipefail` because we intentionally want graceful degradation
# if a downstream pipe element fails (e.g. jq bad-input). Hook chain must never
# block the session.

MANIFEST="${HOME}/.claude/session_manifest.json"
STALE_HOURS="${CLAUDE_SESSION_STALE_HOURS:-24}"
# Configurable via env var — useful for testing (set to 0.001 to force
# immediate eviction) or tightening in pathological cases (long-running /loop
# sessions might want 48h).

if ! command -v jq >/dev/null 2>&1; then
  exit 0
fi
# Fail-open on missing jq. Hooks that fail can break session startup. This
# whole system is a quality-of-life improvement, not load-bearing.

mkdir -p "$(dirname "$MANIFEST")"
[ -f "$MANIFEST" ] || echo '{"sessions": []}' > "$MANIFEST"
# Idempotent bootstrapping. On a fresh install, creates an empty manifest on
# first run. No race: `echo >` is atomic for small content on same FS.

mode="${1:-list}"
# Default mode is `list` — makes manual invocation (`session_manifest.sh`)
# DTRT.

hook_input=""
if [ ! -t 0 ]; then
  hook_input="$(cat || true)"
fi
# `[ ! -t 0 ]` = stdin is NOT a terminal, i.e. hook piped JSON to us.
# If stdin IS a terminal (manual invocation), don't block on cat.
# `|| true` in case cat itself fails for some filesystem edge case.

session_id=""
hook_cwd=""
if [ -n "$hook_input" ]; then
  session_id="$(printf '%s' "$hook_input" | jq -r '.session_id // empty' 2>/dev/null || true)"
  hook_cwd="$(printf '%s' "$hook_input" | jq -r '.cwd // empty' 2>/dev/null || true)"
fi
[ -z "$hook_cwd" ] && hook_cwd="$(pwd)"
# Defensive JSON extraction. Every jq call swallows errors and falls back to
# empty. If the hook payload is malformed or missing expected keys, we just
# proceed as if no data was passed.
# `printf '%s'` instead of `echo` to avoid newline injection issues with
# arbitrary JSON payloads.

now_epoch="$(date +%s)"
cutoff=$((now_epoch - STALE_HOURS * 3600))
# Precompute cutoff once per invocation. Used by both start and stop.

case "$mode" in
  start)
    [ -z "$session_id" ] && exit 0
    # Can't track without an ID — the manifest would have unidentifiable
    # entries. Silently no-op rather than corrupt the manifest.

    branch="$(git -C "$hook_cwd" rev-parse --abbrev-ref HEAD 2>/dev/null || echo '')"
    # `git -C` runs as if cwd were the argument, without actually changing
    # the shell's cwd. Works even if hook_cwd doesn't exist or isn't a repo.

    started="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
    tmp="$(mktemp "${TMPDIR:-/tmp}/session_manifest.XXXXXX")"

    jq --arg sid "$session_id" \
       --arg cwd "$hook_cwd" \
       --arg branch "$branch" \
       --arg started "$started" \
       --argjson now "$now_epoch" \
       --argjson cutoff "$cutoff" \
       '.sessions = ((.sessions // [])
          | map(select(
              (.session_id != $sid) and
              ((.started_epoch // 0) >= $cutoff)
            ))
          | . + [{
              session_id: $sid,
              cwd: $cwd,
              branch: $branch,
              started: $started,
              started_epoch: $now
            }])' \
       "$MANIFEST" > "$tmp" && mv "$tmp" "$MANIFEST"
    # Single jq invocation does three things:
    # 1. Filter out any existing entry with this session_id (dedupe on re-start)
    # 2. Filter out any entry with started_epoch < cutoff (stale eviction)
    # 3. Append the new entry with current state
    #
    # `.sessions // []` handles the case where a manually-edited manifest
    # might have removed the sessions array.
    # `(.started_epoch // 0)` handles legacy entries without the epoch field.
    # `--argjson` (not --arg) for cutoff/now because jq numeric comparison
    # requires actual numbers, not strings.

    peer_count="$(jq --arg sid "$session_id" '[.sessions[] | select(.session_id != $sid)] | length' "$MANIFEST")"
    if [ "$peer_count" -gt 0 ]; then
      peers_text="$(jq --arg sid "$session_id" -r \
        '.sessions
          | map(select(.session_id != $sid))
          | map("  - \(.session_id[0:8])  cwd=\(.cwd)  branch=\(.branch // "n/a")  started=\(.started)")
          | join("\n")' "$MANIFEST")"

      msg="Session coordination: ${peer_count} other Claude Code session(s) active on this machine.
${peers_text}

Before making edits: run \`git log origin/\$(git branch --show-current 2>/dev/null) --oneline -5\`
to check if the peer has pushed. If your intended scope overlaps a peer's active
work, pivot to a different task or ask the user which session should own it.

Manifest: ~/.claude/session_manifest.json (mode: list to inspect)."

      jq -n --arg msg "$msg" '{systemMessage: $msg}'
    fi
    # Emission is conditional on peer existence. No peers => no output => no
    # context pollution in solo-session mode. This matters because 90%+ of
    # sessions will be solo.
    ;;

  stop)
    [ -z "$session_id" ] && exit 0
    tmp="$(mktemp "${TMPDIR:-/tmp}/session_manifest.XXXXXX")"
    jq --arg sid "$session_id" \
       --argjson cutoff "$cutoff" \
       '.sessions = ((.sessions // [])
          | map(select(
              (.session_id != $sid) and
              ((.started_epoch // 0) >= $cutoff)
            )))' \
       "$MANIFEST" > "$tmp" && mv "$tmp" "$MANIFEST"
    # Same dedupe + stale-evict pattern, but without re-appending. Effect:
    # remove this session from the manifest. Stop hook also acts as a
    # secondary stale-eviction opportunity.
    ;;

  list)
    jq --argjson now "$now_epoch" -r \
      '.sessions
        | if length == 0 then "No active Claude Code sessions tracked."
          else
            "Active Claude Code sessions (" + (length | tostring) + "):\n" +
            (map(
              "  - \(.session_id[0:8])\n" +
              "    cwd=\(.cwd)\n" +
              "    branch=\(.branch // "n/a")\n" +
              "    started=\(.started)  (age=\(((($now - (.started_epoch // 0)) / 60) | floor))min)"
            ) | join("\n"))
          end' "$MANIFEST"
    # Human-readable dump. Computes age-in-minutes on the fly from epoch.
    # Empty case handled explicitly (no sessions → single clear sentence).
    ;;

  *)
    echo "Usage: $(basename "$0") {start|stop|list}" >&2
    exit 2
    ;;
esac
```

- No entry ever older than 24h (evicted on next start/stop/list)
- No duplicate session_id entries (filtered on each start)

## 6. Key Decisions Made

Each decision below records: **the choice**, **alternatives considered**, **why the choice was made**, **known tradeoffs**, and **what would cause a future session to revisit the decision**.

### 6.1 Session coordination architecture tier

**Choice:** Tier 1 — file-based manifest at `~/.claude/session_manifest.json`, managed by a bash hook script.

**Alternatives considered:**
- **Tier 2 — scope-claim empty commits.** Each session pushes `chore(claim): session-<id> working <scope>` as an empty marker commit at start. `git log --grep='^chore(claim):'` shows active claims. Session-stop hook force-pushes a deletion or follows up with `chore(release):`.
  - **Why rejected:** Git history pollution (hundreds of claim commits per week), requires force-push in cleanup (risky), creates a coordination point that itself races across sessions.
- **Tier 3 — coordinator daemon (localhost:9100).** A Bun/Node service exposes `POST /claim`, `GET /active`, `DELETE /claim/:id`. Sessions query it via an MCP tool.
  - **Why rejected:** Infrastructure weight is disproportionate for a 2-session coordination problem. Requires supervisor (systemd/pm2), port management, health checks. If the daemon dies, all sessions coordinate through nothing.
- **No coordination (status quo).** Let sessions race; rely on human operator to notice.
  - **Why rejected:** User explicitly asked "how can we create a system to recognize this more quickly"; status quo fails that requirement.

**Why Tier 1 won:**
- **Zero new runtime dependencies** beyond `jq`, which is already installed
- **File-based state** is inspectable with any text editor; no opaque daemon state
- **Hook-driven lifecycle** is native to Claude Code's architecture — no new mental model
- **Atomic rename on NTFS** provides the concurrency safety we need without any lock files or coordination protocol
- **Cost of being wrong** is low: if Tier 1 proves insufficient, upgrading to Tier 2 is additive (the manifest can coexist with claim commits)

**Tradeoff:** Manifest reflects only session identity (id, cwd, branch), not intended scope. Two sessions on the same branch could still stomp each other on the same files. **This is acceptable** because the peer-report alert lets the reader take responsibility for scope-negotiation, which is the behavior change we actually wanted.

**Revisit if:** Running >2 parallel sessions becomes routine, or the scope-collision rate exceeds ~10% of session-starts.

### 6.2 Stale-eviction cutoff: 24 hours

**Choice:** Evict manifest entries older than 24h on every start/stop/list.

**Alternatives considered:**
- **1 hour.** Aggressive; would falsely evict live long-running sessions.
- **12 hours.** Still aggressive for overnight /loop runs.
- **48-72 hours.** Too lax; stale entries would linger visibly in `list` output for days.
- **No eviction (persistent manifest).** Requires explicit cleanup on crash; ghost entries accumulate forever.

**Why 24h:** Trading sessions can span 8-12h of deep work plus overnight test runs and /loop cycles. 24h is approximately 2× the longest plausible active session. Aggressive enough to clean crash-residue within a day; loose enough to never evict a live peer.

**Implementation detail:** Exposed via `CLAUDE_SESSION_STALE_HOURS` env var. Users running genuinely longer sessions can override at shell init without editing the script.

**Tradeoff:** A session that crashes 23h in leaves a ghost entry that could confuse a 24th-hour peer. Mitigation: the ghost entry ages out within that peer's working window.

**Revisit if:** Observed false-positive evictions (eviction of a live session) ever occur.

### 6.3 Failure mode: fail open

**Choice:** If `jq` is not installed or if any hook-path error occurs, exit 0 silently.

**Alternatives considered:**
- **Exit 1 on missing jq.** Would block session start. User's session startup would hang on this hook until timeout (5000ms), then proceed anyway. Negligible benefit, real cost.
- **Log error to stderr, exit 0.** Still fails open but surfaces the error. Risk: stderr gets captured into Claude Code context and pollutes every session with "jq not found" noise if the user ever uninstalls jq.
- **Emit a `{"systemMessage": "..."}` warning.** Would inject a warning into context on every session. Overkill.

**Why silent exit 0 won:** Session coordination is a quality-of-life improvement. It must never block the user from starting a session. A user working on a fresh machine without jq should have Claude Code behave identically to a user with jq installed, modulo the coordination feature's absence.

**Tradeoff:** A user might never notice that jq is missing and that coordination isn't actually working. Mitigation: the auto-loaded rule file (`session_coordination.md`) notes "jq not installed → silent no-op" under Failure Modes, so anyone reading the rule learns the invariant.

### 6.4 Hook placement: last in each array

**Choice:** Append the manifest hook as the *last* matcher-element in both SessionStart and Stop arrays.

**Alternatives considered:**
- **First in array.** Would run before the second-brain vault hook and the system32-warning hook. Would mean the manifest's peer-report system message arrives in context before the other hooks' messages.
- **In a dedicated new key (e.g., `SessionReady`).** Claude Code doesn't support custom hook names; must use the documented event names.

**Why last won:** Upstream hooks establish state (vault warmup, system32-warning). Running after them means the manifest hook sees final state, and its peer-report (if emitted) lands *after* the other system messages in context order. This keeps the coordination message closest to the actual conversation start, maximizing its relevance-weight in the model's attention.

**Tradeoff:** None apparent. Order-sensitivity was reasoned about but no realistic scenario exists where first-order execution helps.

### 6.5 Rule-file location: `~/.claude/rules/` (not a project-level CLAUDE.md)

**Choice:** Put the coordination rule in `~/.claude/rules/session_coordination.md` so it auto-loads globally.

**Alternatives considered:**
- **Project-level** `jarvis-trader/CLAUDE.md` import. Would require editing the trader project's instructions and wouldn't help GMS or master-jarvis sessions.
- **Separate CLAUDE.md at `~/.claude/CLAUDE.md`.** Claude Code does read `~/.claude/CLAUDE.md` but the user's current setup loads `~/.claude/rules/*.md` instead. Inserting a new CLAUDE.md would introduce a loading-mechanism duplicate.

**Why the rules/ directory won:** Empirically matches the user's existing pattern (`token-efficiency.md`, `workflow.md` live there). Zero new conventions introduced; follows the principle of least surprise.

**Tradeoff:** If Claude Code ever changes the auto-load mechanism for `~/.claude/rules/`, the coordination rule silently stops loading. Mitigation: the rule content is short, so re-discovering and re-wiring is cheap.

### 6.6 Branch-field capture: at start time only

**Choice:** Record the branch name when the session starts; do not update if the user switches branches mid-session.

**Alternatives considered:**
- **Update branch on every hook invocation (UserPromptSubmit).** Would require wiring a third hook. Overhead on every prompt.
- **Periodically refresh via background task.** Too complex for the benefit.
- **Drop branch field entirely.** Reduces peer-report usefulness.

**Why start-time-only won:** Peer sessions primarily care about *cwd collision*, not branch drift. A peer on the same cwd but a different branch is still at risk of file-level collision (Git operations don't respect branch membership for dirty-tree edits). So the branch field is *informational* rather than *load-bearing*; freshness isn't critical.

**Tradeoff:** If a session starts on branch A, switches to branch B, and a peer later starts on branch A, the peer sees the original session as still on A when it's now on B. Acceptable false-positive; the peer's correct action (check git log, consider scope) is the same either way.

### 6.7 Stay in this session vs. fresh session for Tier-1 build

**Choice:** Build Tier-1 in the current (already-running) session.

**Alternatives considered:**
- **Start a fresh session.** Clean context, full MEMORY.md load, no compaction baggage. User offered this explicitly.

**Why stay won:** I already had full context on the design (having just proposed it in the previous turn). A fresh session would re-read MEMORY.md, re-load rules, re-orient on the branch — the exact boot-cost the Tier-1 system was being built to eliminate. Net negative.

**Tradeoff:** Output-token budget depletion in this session, which actually occurred and triggered the token-limit event before this expanded handoff could be fully written in one pass. **This was the cost paid.** In hindsight: accepting the boot-cost of a fresh session might have been cheaper than two rounds of writing this handoff. Mitigation: write-in-chunks pattern using Edit append calls, which is what this expanded rewrite uses.

**Revisit if:** A future similar "infrastructure build in a mature session" request arises. Heuristic: if remaining output budget < 15K tokens estimated for the work + documentation, prefer a fresh session.

### 6.8 Not fixing the untracked files

**Choice:** Leave `HANDOFF-2026-04-22-0006.md` and `mnq_breakout_search_results.json` untracked pending user direction.

**Alternatives considered:**
- **Commit them.** Fastest way to clean git status. But shared-visibility action without explicit authorization.
- **Add to .gitignore.** Permanent fix but hides the files from collaborators.

## Appendix D — Glossary of Domain Terms (For AI Readers)

Terms used throughout this handoff that might not be obvious from context:

**Gate v2:** JARVIS TRADER's strategy-routing gate. Dual-pathway (CORE + ALT) with four criteria per pathway: `mbb_pf_ci_lower` (block-bootstrap PF CI lower bound), `p_positive_edge` (bootstrap probability of positive edge), `mc_95_dd_pct` (Monte Carlo 95th percentile drawdown), `dsr` (deflated Sharpe ratio). Phase 3-FULL = hard enforcement in routing; Phase 3-LIGHT = advisory readers.

**DO_NOT_TRADE_SYMBOLS:** A `frozenset` in `engine/backtest/signals.py` listing symbols whose `entry_signal` is force-overridden to `NO_TRADE`. Currently `{"MCL", "MNQ"}`.

**TV MCP / TV Tier 0:** TradingView Desktop running with Chrome DevTools Protocol on port 9222. The engine's `market_data.get_bars()` checks TV first (Tier 0) before IBKR (Tier 1), Polygon (Tier 2, equities only), CSV cache (Tier 3). P0.2 shipped this.

**Forward-recorder:** Observational scheme where the engine records a "hypothesis row" at market open (08:30 CT) and fills the outcome at close (15:15 CT) for MES. Does NOT trade; feeds `forward_recorder_metric` into agent prompts.

**APScheduler:** Python cron-like scheduler registered in the engine's FastAPI `lifespan`. Jobs: `weekly_gate_v2` (Sat 01:00), `mes_session_recorder` (08:30 Mon-Fri), `mes_session_outcome` (15:15 Mon-Fri).

## Appendix G — Deep Insights (Expanded)

The short `✶ Insight ─` blocks scattered through the session conveyed one-line observations. This appendix unpacks the load-bearing ones at length, for a future reader who wants to understand *why* the design is the way it is — not just what it does.

### G.1 Why Atomic Rename Is Actually Atomic on NTFS (And Why That Matters)

The manifest is written via the `mktemp → jq > tmp → mv tmp MANIFEST` pattern. This is the classic "write then rename" atomic-update pattern that's been idiomatic in POSIX systems since the 1980s. The correctness argument rests on three claims:

1. **`mv` on the same filesystem is an atomic rename.** On POSIX, `rename(2)` guarantees that either (a) the destination has the new content, or (b) the destination still has the old content; never a torn/partial state.

2. **Readers either see the old version or the new version, never both.** Any process that opens the manifest file between `jq >` start and `mv` end either finds the original unchanged file (if they hit before the rename) or the new file (if after). The temp file isn't linked at `MANIFEST` path until the rename completes.

3. **Concurrent writers don't lose data.** If session A and session B both write to their own temp files and both rename to `MANIFEST`, one of the two renames wins. The loser's content is overwritten, but critically, the loser's temp file's content is the full new manifest (with all its own changes). The winner's content is also a full new manifest. **The inclusion of stale-eviction on every write means that even a losing race isn't catastrophic** — the next write by either session will re-read the winner's manifest and include its own changes atop.

**But does Windows NTFS honor these semantics?**

Yes, with caveats. NTFS implements `MoveFileEx` (called by `mv` in git bash via `rename(2)` POSIX emulation) with `MOVEFILE_REPLACE_EXISTING` set when the target exists. The underlying operation is a transacted metadata update: the directory entry for `MANIFEST` swaps its pointer from the old inode to the new inode in a single filesystem-journal entry. A crash during this swap either leaves the old pointer intact (no corruption) or the new pointer written (rename completed).

The caveats are:
- **Cross-filesystem renames are NOT atomic** — they become a copy+delete. Our script uses `${TMPDIR:-/tmp}` which on git bash is `/tmp` (mapped to `C:\Users\mattm\AppData\Local\Temp\`) by default. The manifest lives in `~/.claude/`. If both are on `C:\`, they're the same volume and rename is atomic. If the user sets `TMPDIR` to a different volume, rename becomes copy+delete and the guarantee breaks.
- **Antivirus scanning** can introduce a window where the file is briefly inaccessible. Unlikely to matter for a 1-2KB JSON file.
- **OneDrive or similar sync tools** might open the file for reading during sync, potentially blocking the rename. `~/.claude/` is not typically synced by default.

**For this specific use case**, the atomicity is overkill — we're writing a tiny JSON file from a few-times-per-day hook. Even if a torn write occurred, the next start/stop invocation would overwrite it. The atomicity exists as a correctness guarantee the reader shouldn't have to think about, not as a critical reliability feature.

### G.2 Why 24 Hours Is The Right Stale-Eviction Cutoff

Choosing a TTL requires reasoning about both directions: too-short causes false eviction of live sessions; too-long lets ghost entries pollute the manifest indefinitely.

**Session-length distribution on this machine** (from memory analysis of prior session lengths):
- 50th percentile: ~2-4h (typical focused work)
- 90th percentile: ~8h (deep work with compaction cycles)
- 99th percentile: ~16h (overnight /loop runs, extended debug sessions)
- Absolute max observed: ~24h (multi-day sessions without restart are rare)

**The 24h cutoff is approximately 1.5× the 99th percentile.** This is a deliberate choice: we want false-eviction probability to be near zero, because false eviction means a live session is coordinated-invisible to its peers. The cost of a false eviction is exactly the problem we built Tier 1 to solve.

**The cost of letting a ghost linger for up to 24h** is minimal: the peer report lists it, a peer sees `age=1440min` and recognizes the entry is stale. No actual coordination action gets taken against a ghost.

**Alternative values considered:**
- **6h:** Would cut 10% of long sessions. Too aggressive.
- **12h:** Would cut 1% of long sessions. Borderline.
- **48h:** Would let ghosts from 2 days ago pollute peer reports. Excessive.
- **No TTL (persistent manifest):** Requires explicit manual cleanup. Worst of all options.

**The env-var override (`CLAUDE_SESSION_STALE_HOURS`) exists** because the heuristic is fundamentally empirical and subject to workflow drift. If the user starts running routinely longer sessions, bumping to 48h is a zero-code change.

**Consequence for the peer-report message:** The report includes the session's `started` timestamp. If a reader sees a peer from 18h ago, they can reasonably judge "this is probably a ghost" without the manifest actively evicting it. **Human-in-the-loop makes the exact TTL less critical.**

### G.3 Hook Output Format: Why `{"systemMessage": "..."}` Is the Right Shape

Claude Code hooks communicate with the session by emitting JSON to stdout. The schema (per the Claude Code docs) supports several fields:
- `systemMessage`: inserted into the conversation as a system reminder
- `additionalContext` (newer): appended to session context without being a "message"
- `additionalSystemPromptText`: injected into the system prompt itself
- Empty output: no-op

**Why `systemMessage` over the alternatives:**

The peer-report content is (a) situational (relevant only if peers exist), (b) time-stamped, (c) actionable (the reader should consider their scope). These characteristics map to a system reminder, not an always-on prompt injection.

**Why a single string, not a structured object:**

Claude Code's `systemMessage` field takes a plain string. Markdown is rendered. No structured fields. This is appropriate because the downstream consumer is an LLM, not a machine parser — human-readable beats structured for this audience.

**Why emit nothing on zero peers:**

If a hook always emits a system message, even saying "no peers detected", every solo session gets context pollution. Over many sessions this is noise that the model must process. **The silent-on-no-peers pattern is the hook equivalent of "don't log what didn't happen."**

**Why the message ends with a command suggestion, not a command execution:**

The message includes `run \`git log origin/...\`` as a textual suggestion. We don't execute the git log in the hook and inject its output. Reason: git log output can be long, timing-variable, and the hook runs pre-session-context; we don't know the session's attention budget. Telling the reader what to run lets them decide if they need to, rather than forcing them to process the output.

### G.4 Why Rules Load From `~/.claude/rules/*.md` (And What That Means For This Design)

The auto-loading mechanism for `~/.claude/rules/*.md` is not officially documented in the public Claude Code changelog (as of the model's knowledge cutoff). Empirically, the user's context at session start includes the contents of both `token-efficiency.md` and `workflow.md` prefixed with "(user's private global instructions for all projects)". This is consistent across sessions and survives compaction.

**Implications for the session_coordination.md file:**

1. **It will auto-load on every future session on this machine.** Even sessions on unrelated projects (GMS, master-jarvis, system32) will see the rule. This is fine — the rule's advice is universal: "if you see peer-session alerts, check git log before editing."

2. **It competes for context with token-efficiency.md and workflow.md.** Three rule files means the model must parse and maintain attention over more total rule content per session. We should write the rule to be terse and action-forward; if it grows bloated, all three rules lose effectiveness.

3. **If Claude Code ever changes the rule-loading mechanism, our rule silently stops being loaded.** Mitigations: the rule content is short enough to re-write from scratch; the hook still functions without the rule (it just emits a systemMessage directly).

4. **Rule order matters empirically but is not user-controllable.** Claude Code appears to load rules alphabetically or by directory listing order. `session_coordination.md` sorts between `token-efficiency.md` and `workflow.md` (alphabetically: s < t < w). Effect: session-coord rule is surfaced after workflow.md, which is reasonable; session-coord is more specific and "deeper" than workflow.

### G.5 Why We Don't Propagate Session Scope Via Git Commits (The Tier-2 Temptation)

Tier 2 — scope-claim empty commits — is superficially attractive:
- Distributed: every teammate's git history shows who's claiming what
- Survives machine restarts (commits are persistent)
- Works across machines (if sessions are on different hosts)

But we rejected it. Why?

**First-order objection:** git history noise. Every session adds 1-2 commits. Over a week of 10 sessions, that's 20 claim commits mixed into actual-code commits. Bisect tooling, changelog generation, and human reading all suffer.

**Second-order objection:** force-push dependency. Releasing a claim requires either (a) pushing a `chore(release):` commit (more noise) or (b) force-pushing to remove the claim. Force-push is explicitly restricted by the user's workflow rules ("Never force push to main/master"). The claim-branch would become yet another piece of git plumbing to keep clean.

**Third-order objection:** race conditions on the claim itself. Two sessions trying to claim the same scope would both push; one would fail on fast-forward, the other would succeed. The losing session doesn't know it lost until it tries to push. We'd need to add a retry loop. Complexity climbs.

**Fourth-order objection:** wrong abstraction. The problem is "two sessions are about to edit overlapping files on the same machine." The solution is a per-machine file registry, not a per-repo git commit. File-based solutions are local; git-based solutions implicitly require network round-trips.

**When would Tier 2 actually be right?** Cross-machine coordination. If the user routinely worked on the same branch from a laptop and a desktop simultaneously, file-based Tier 1 wouldn't help. But that's not the observed failure mode; both tonight's sessions were on the same machine.

### G.6 Hook Placement Order: Why Last Is Right

Hook arrays in `~/.claude/settings.json` fire in order. SessionStart has 3 entries after our edit: system32-warning → second-brain-vault → session-manifest. The manifest is last. Why?

**Hypothesis tested:** upstream hooks might modify the environment in ways that affect our hook's behavior. For example, the system32-warning hook might inject a systemMessage; the vault hook might write files under the session's cwd. If we ran first, our peer report would come first in context, possibly crowding out the other hooks' messages.

**What actually happens in Claude Code hook execution:**

Hooks run sequentially; each hook's stdout is captured and processed in order. The resulting systemMessage entries are inserted into the session in the order they were emitted. So running last means:
- System32-warning appears first in context (if cwd is system32)
- Second-brain vault setup happens second
- Our peer report appears last, closest to the conversation-start boundary

**Why that's the right order:**

1. **Context attention decays with distance from the conversation.** The model pays more attention to recent context. Our coordination message is the most immediately actionable ("don't edit peer's files"); putting it last means it's closest to the model's active attention window.

2. **System-setup messages are "background"; coordination is "foreground".** System32-warning and vault-setup are orientation messages the model uses to set up state. Our coordination message is a call-to-action for the session's behavior. Action items belong near the front of the model's attention.

3. **Our hook's emitted systemMessage can include "context pointers" to the earlier hooks' outputs** — e.g., we could say "if you're in system32, see the earlier warning." Running first, we couldn't cross-reference. Running last, we could (we don't, currently, but the option exists).

### G.7 The "Fail Open" Philosophy (Hooks That Never Block)

Every non-critical hook on this machine fails open. The session_manifest hook joins that pattern:

- `command -v jq` fails → exit 0 silently
- `git -C ... rev-parse` fails → empty string, not abort
- Malformed stdin JSON → treat as no-op, not error
- Missing session_id → no-op, not error

**Why:** Hooks run during session boundaries (start/stop). A hook failure during start can block the user from interacting with Claude Code entirely. A hook failure during stop can prevent the session from cleanly closing. Neither failure mode is acceptable for a quality-of-life feature.

**Explicit tradeoff acknowledged in Section 6.3:** We lose the ability to tell the user "your coordination system is broken." They might go months with the hook silently no-op-ing before realizing peers aren't being detected.

**Mitigations:**
- The rule file documents the silent-failure mode
- The `list` command is a self-diagnostic ("does this print real peers?")
- If the user debugs a peer-collision and finds coordination wasn't working, they'll discover jq is missing or similar

**Alternative considered:** Tier the failure modes. Critical failures (no session_id passed) exit 0 silently; recoverable failures (jq missing) emit a one-time warning to stderr that might reach context. Decided against: the warning would fire on every session-start if the condition persisted, causing noise. Silent-always is simpler and only slightly less diagnostic-friendly.

### G.8 Why Session_ID Alone Is Sufficient Identity (No PID / TTY / Hostname)

Each manifest entry stores `session_id` as the unique identifier. We could have included:
- `pid` (claude-code process ID)
- `tty` (terminal device)
- `hostname` (for cross-machine scenarios)
- `user` (the OS user)

We store none of these. Why?

**`session_id` is already unique.** Claude Code generates a UUID per session. Two sessions can't share one. Adding more identity fields is redundant for local uniqueness.

**PID is unreliable across OS restarts.** PIDs get reused. If a session dies and the OS reuses its PID for another process, a stale manifest entry with that PID would be misleading. We prefer our own 24h TTL over PID-based freshness detection.

**TTY is both unreliable and privacy-leaky.** Some Claude Code invocations don't have a TTY (headless, from MCP, etc.). Storing the TTY assumes a deployment model that's no longer universal.

**Hostname is useful only for cross-machine scenarios**, which we're explicitly not solving. If we ever add cross-machine coordination (Tier 3 daemon), hostname would be added at that point.

**User is implicit in the manifest's path.** `~/.claude/session_manifest.json` is per-user already; multi-user scenarios are excluded by filesystem isolation.

### G.9 What Could Go Wrong: Known Failure Modes Enumerated

In roughly decreasing likelihood:

1. **User uninstalls jq.** Hook fails open silently. Coordination stops working. Mitigations: rule file documents this; `list` command returns command-not-found style error which is diagnostic.

2. **Manifest file manually edited and left malformed.** Hook's jq ops fail, `> $tmp` leaves empty tmp file, `mv` replaces manifest with empty file. Self-heals on next start (the `[ -f "$MANIFEST" ] || echo '{"sessions":[]}' > ...` line re-initializes). But between the corruption and the self-heal, peer reports are wrong.

3. **Race between two session-starts in the same second.** Both sessions write temp files; one `mv` wins. The loser's content (which includes itself + evicted-stale) overwrites, but doesn't include the winner. Next session-start (even just running `list`) re-reads, and because both sessions also appended themselves, one session is missing. **This race is real.** Mitigation: realistic rate of session-starts is <1/minute; the race window is <100ms; probability is negligible. If it ever bit us, we'd add `flock(1)` around the jq operation.

4. **Clock skew between sessions.** If the system clock is adjusted (NTP sync, user fix), `started_epoch` values can be inconsistent. Stale eviction might evict live sessions or preserve dead ones. Mitigation: system clocks are usually accurate to seconds; the 24h TTL is coarse enough to absorb minutes of skew.

5. **Hook timeout.** The script has a 5000ms timeout per hook. Normal runtime is <100ms. Only a pathological git-repo state (corrupted, network mount, etc.) would approach the timeout. Claude Code would kill the hook; session proceeds without the start entry.

6. **Claude Code changes hook input format.** If a future version passes different JSON keys (e.g., `.sessionId` instead of `.session_id`), our extraction returns empty, script no-ops. Mitigation: check Claude Code changelog periodically.

7. **User changes home directory path.** `${HOME}/.claude/...` resolves wrong. This would have catastrophic effects far beyond this hook; not specifically our problem to mitigate.

8. **Hook interferes with existing hooks' output.** Our hook is last in each array; upstream hooks finish before ours runs. No interference observed in smoke tests.

### G.10 The Meta-Lesson: When To Build Infrastructure vs. Accept Overhead

The user's meta-question was essentially "was the overhead worth the cost of building prevention?" The answer is nuanced:

**This session built Tier-1 coordination at a cost of ~25,000-30,000 output tokens** (including the initial design conversation, the build itself, the smoke tests, the wiring, and now this expanded handoff). The observed overhead it saves is ~5-10% per-session token cost from stale-recap reconciliation and cross-session coordination gaps.

**Break-even analysis:**
- Session uses ~200K-400K input tokens typically
- 5% overhead ≈ 10-20K tokens
- Break-even after ~1-2 future parallel sessions where Tier 1 avoids the full overhead
- Expected future parallel-session rate on this machine: ~1-2 per week

**Break-even in ~1 week.** Infrastructure build was worth it.

**Generalization:** Build coordination infrastructure when (a) the friction cost exceeds the build cost within 2-3 expected uses, AND (b) the friction is latent (users don't notice until asked), AND (c) the infrastructure doesn't introduce new failure modes of its own. All three are true for Tier 1 as built.

**Contra-example:** Would Tier 2 (scope-claim commits) have been worth building? Build cost: maybe 2× Tier 1 due to the force-push cleanup plumbing. Overhead saved: marginally better than Tier 1 (fine-grained scope declarations vs. cwd/branch). Infrastructure risk: force-push-in-cleanup is a failure mode Tier 1 doesn't have. Break-even would be further out, and the failure-mode penalty could wipe out the savings. **Not yet worth it.** Revisit when Tier 1 proves insufficient.
