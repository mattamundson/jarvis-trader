## Root cause #1 — `corey_alerts` 16-month "staleness" is correct

The source channel `⏰-trade-alerts` (channel ID 1130292150962245642) has 70 total
messages and the LAST one is 2024-12-31T09:03 by `tathedog` (Corey):

```
2024-12-31T09:03:21 | tathedog | That's TWO big wins today. Don't overtrade and blow it 🙂
```

Corey stopped posting in `#trade-alerts` on New Year's Eve 2024. All 70 messages from the
channel's lifetime are already imported into `discord_corey_alerts`. The table is not
stale — it's *complete through the channel's end-of-life*.

Corey's activity migrated to `#general` (channel 741484321142997086) where his last post
is 2026-04-01T16:32 — that channel powers `discord_corey_commentary` (64k rows) which IS
fresh.

**Verified**: no agent consumes `discord_corey_alerts` during decision-making. The only
reader is the HTTP dashboard endpoint `GET /discord/corey-alerts` in
`engine/routers/discord_router.py:114`. Agents consume `corey_session_bias`, which is
derived from `discord_corey_commentary` in `engine/discord/commentary_processor.py`.

**Conclusion**: The 16-month figure is a data-end, not a pipeline-break. Zero decision impact.

## Root cause #2 — real staleness is 15 days, on the JSON exports

All 30+ JSON files in `C:\Users\mattm\discord-export\` are dated 2026-04-02. The nightly
scheduler at `engine/main.py:1483-1527` fires Mon–Fri 06:00 CT and runs:

1. `run_discord_import()` → reads JSONs, inserts rows into SQLite
2. `run_sentiment_etl()` → computes sentiment aggregates

It does **not** run DiscordChatExporter (DCE). DCE is a separate manual step. Last run:
2026-04-02 (see `docs/session-logs/discord-export-session-2026-04-02.md`).

The import pipeline is healthy. It is correctly detecting "no new JSON content" on each
run, so nothing new enters the DB.

`engine/logs/nightly_discord.log` confirms:
```
2026-04-16T23:43 ... Results: {'etl': {'status': 'ok'}}
```
No `import` key in results → only ETL ran (via `--etl-only` CLI flag, manual invocation).
The scheduler wasn't triggered since Mon–Fri 06:00 CT hasn't arrived since the last JSON
refresh — and even if it had, there's no new JSON to import.

## Why I didn't auto-schedule it

1. **Bandwidth**: active channels total ~310 MB per full re-export (#general 173MB +
   indicator-alerts 2MB + 9 instrument channels 30–100MB each). Nightly × 5 nights/week
   = ~1.5 GB/week. User should decide if that's acceptable.
2. **Discord token risk**: the token lives in `C:\Users\mattm\discord-export\.token`.
   Scheduled automation multiplies the surface area for credential rotation/leak.
3. **DCE incremental mode**: `--after <date>` works but writes separate files per run.
   Our importer expects one JSON per channel. Either the importer needs to merge or the
   scheduler needs a "download full then replace" step — both are design changes, not
   one-line cron additions.

These are real tradeoffs that deserve a user decision, not a silent wire-up.
